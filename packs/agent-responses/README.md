# Responses transport

ValidateConfig(config)->JSON is local validation only. ProviderBody implements Agent::Provider(config,execution,operation,payload)->event JSON. A consumer selects it through ordinary provide; default Agent remains unconfigured. Required protocol responses and explicit endpoint/model; keys are never accepted in config. keyEnvironment names only an external environment binding. Secrets are read only after explicit per-run content approval pinned to endpoint/model/project; external hosts additionally require usage approval. Browser/Android direct key access is refused. No redirects, automatic request retries, credential persistence, auth creation or project enumeration.

Uses BCL HTTP, bounded25s requests,1MiB replies,1..8 rounds and32KiB generated text. Response must be completed; incomplete/refusal/error cannot silently complete work. Preserves all response output items before function outputs. Parallel tool calls disabled. Definitions from the granted local DevelopmentTools capability; hashed execution+call ID dedup keys. Only approved message/context/task projection and intended tool results are transmitted; authorization, local capability and credential binding names are omitted. WorkerTasks' actual kind/project/input envelope is supported and cannot change assigned project. Configuration, per-run approval and opaque capability remain separate.

cancel is sticky before/after open, late events are fenced. close cancels/joins1500ms, retains ownership for retry on a pending task; it does not pretend to roll back staged changes. Agent's outer timeout/policy is still consumer owned. No streaming HTTP support yet; bounded text events are delivered after a complete response. Provider completion never marks WorkerTasks completed or confirms sources.

Outside reads: Agent Provider/Start/Poll/Close, WorkerTasks Command's public execution envelope, DevelopmentTools Definitions/Snapshot/Invoke, official API documentation below. No outside implementation edits in this increment beyond test-runner registration. Rebuild scope: Agent.Responses contracts/body and chosen consumer links; existing Agent implementation is unchanged.

Official sources checked2026-10-09: [API authentication](https://developers.openai.com/api/reference/overview) (server-side credentials; client apps require a relay), [function calling](https://developers.openai.com/api/docs/guides/function-calling), [Responses manual history](https://developers.openai.com/api/reference/typescript). SDK not installed. Only the owned loopback protocol fixture ran; no API account, credential read or external model call occurred. See ../ai-connection/README.md for gate/evidence and remaining integration.

Public Provider(config,execution,operation,payload)->JSON is backed by AdapterBody using the same owned Provider.csbody source. Consumers can call the qualified API provider without overriding Agent defaults globally; explicit Agent::Provider composition remains available through ProviderBody. Connection metadata declares the qualified public function. No generic runtime loader or core dispatch was added.
