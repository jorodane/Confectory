# Project Chat

`Confectory.ProjectChat::OpenHost(hostStorage, projectId, hostParticipant)` is an optional local text model. The trusted composer supplies a private, machine-local storage directory, the existing durable project UUID, and the host identity. It holds one active owner per project and storage directory and closes that owner when the host stops. The model does not authenticate caller-supplied identities.

The returned native handle is a tuple of `Join`, `Send`, `Read`, and `Close`. Only the composer holds that handle. After admitting a participant, it gives the connection only the tuple of `Send`, `Read`, and `Leave` returned by `Join`. The connection uses the admitted identity for every send and can read only messages committed after it joined, including its own messages. `Leave` revokes that connection. `Close` revokes all connections. Each `Read` returns ordered JSON rows containing `id`, `sender`, and `text`.

The host commits to `project-chat/<projectId>.json` inside its local storage before a successful send becomes visible. All public messages use that one journal. The model does not open a participant or Helper store. Reusing the same lowercase GUID in `N` form with the same sender, text, and attachment snapshot acknowledges the original commit without appending or delivering a message. Reusing it for a different submission fails. A conflict between host writes requires reopening the host. The bounded model rejects more than 256 messages, 4 MiB of journal data, or 16 simultaneous connections per host.

`OpenHostWithAttachments(hostStorage, projectId, hostParticipant, manifest)` uses the same host model. Its host and connection handles append `SendAttachment(messageId, text, box)` and `ReadAttachment(messageId)`. The trusted composer supplies the canonical manifest of the already selected project. A send requires a sealed YogiBox bound to that exact manifest, project, and sender. The local receiver commits the frozen description, LaY image data, and EY references with the message. Attachment reads require access to that message in the host history or in the connection's own inbox. Message lists only expose an attachment ID. A consumer resolving an EY still needs its own authorized workspace access. The original YogiBox receiver selection and default refusal remain in place.

The existing text handle and v1 text-only journals still work. The first attachment upgrades the same journal to v2 and binds attachment access to a hash of the canonical manifest path. Readers predating v2 refuse that journal. No separate attachment file is created.

The desktop EditorHome bridge declares the read-only `readPublicChatHistory` observation. It accepts an empty input and uses the active session's verified local creator, original manifest, and profile storage. It reads the journal bound to the local editor participant `local-user`. It returns ordered message rows and attachment IDs with the current `projectActivation`. Home, revoked authority, and an unreadable journal return an unavailable status without message data. An authorized view with no journal returns an empty list without creating a file. A new activation invalidates older mounted scopes, including after reopening the same project. The Chat surface displays stored rows in its existing list with a public sender prefix and keeps the existing Helper output and composer independent.

`readPublicChatAttachment` accepts the exact `messageId` and `attachmentId` from a history row. It returns the frozen description and item metadata. `readPublicChatFirstImage` and `readPublicChatSecondImage` take the same pair and read at most one bounded LaY capture per observation. An EY target is exposed only when both the active owned draft and the current manifest identify the registered declaration. The viewer rereads that authorization before invoking the editor's existing selection action. On project activation change or authority loss, it discards pending replies and clears the display. The bridge does not retain a host handle, write a journal, or send a message.

`Confectory.EditorHome::LocalPublicChat` is the in-process adapter used by those observations. Its internal `send-text` operation accepts the active editor session and activation, a stable message ID and text. It derives the project, storage and sender from the verified creator's active editor and rechecks the original before committing. Sends on an active invitation session share its host handle. Without an active room, each call opens and closes the journal handle. A stale activation, closure or missing creator proof refuses the operation. It uses the same journal and retry rules as the model. The default WebUI and MCP expose no send, issue or join entry. The existing composer continues to submit Helper requests.

For a sealed Yogi already owned by that editor window, `prepare-attachment` takes the message ID and returns a selection ID. It pins the live seal to the window and project activation using the trusted snapshot's digest. The editor retains just that selection in memory. `cancel-attachment` discards it. `send-attachment` takes the selected ID, the same message ID and the explicit text. It checks the current seal again and delegates to the existing atomic message-plus-attachment commit. Preparation and cancellation leave the journal and private Yogi files alone. An exact retry with the live selection acknowledges the same message. Leaving the project, changing the box or losing proof prevents reuse of the old selection.

`Confectory.EditorHome::PublicChatInvitations` returns native `Issue(seconds)`, `Accept(projectId, code, displayName)`, and `Close()` capabilities for a verified creator's active editor session. The internal `issue-invitation` operation uses a five-minute lifetime. A host keeps at most 16 outstanding invitations and retains only their hashes and deadlines in memory. Redemption checks the project and host, admits one connection and consumes the code under the same lock. The host assigns a distinct actor to each admission and appends its identity to the display label. Each connection starts with an empty inbox and receives later commits, including its own. Leaving clears its inbox. Closing the room, switching projects or detecting loss of creator proof revokes all its codes and inboxes. A second window in the same editor process cannot claim the active room or write outside it. Existing journal CAS governs writers in separate processes.

MultiPlay's loopback handshake uses one room capability and accepts the participant label from each caller. The source-editing adapter manages drafts for a shared project path, and Sites pairing authorizes requests to the engine tool bridge. Public chat uses its own admission.

The optional native `StartPublicChatLoopback` development entry requires `CONFECTORY_DEV_PUBLIC_CHAT_LOOPBACK=1`, the verified active creator and a supplied TLS certificate with a private key. It binds an ephemeral IPv4 loopback port. `ConnectProtectedLoopback` takes the independently trusted public development certificate, validates the localhost name and chain with .NET TLS, and requires an exact certificate match before sending the invitation. This entry uses a pinned local trust anchor with no external revocation or certificate downloads. [TLS certificate policy](https://learn.microsoft.com/en-us/dotnet/api/system.net.security.sslclientauthenticationoptions.certificatechainpolicy) · [TLS server name validation](https://learn.microsoft.com/en-us/dotnet/api/system.net.security.sslclientauthenticationoptions.targethost)

The native `OpenProtectedChat` owns the streams supplied by an explicit listener factory. `ConnectProtectedChat` receives a separate stream factory, the expected TLS DNS name, and the host's public pin from the trusted invitation handoff. It validates the name and pinned chain before sending the one-use secret. The factories own address selection, binding and dialing. The transport core knows the host authority, project, invitation and live connection without resolving addresses or publishing ports. `StartPublicChat` applies the original creator check, room ownership and lifecycle to the supplied native listener.

EditorHome uses only the development loopback adapters. The existing card carries the ephemeral port, project UUID, public certificate and one-use secret. The adapters select IPv4 loopback and the `localhost` TLS identity. The browser bridge supplies neither a native transport factory nor an endpoint. The current Chat UI, private history and public journal retain their existing boundaries.

The server keeps each admitted connection's capabilities in its socket worker. Join acknowledgements and message rows carry no connection identity. The worker calls `Leave` after EOF, timeout or cancellation. Closing or switching projects stops the listener, and a periodic host check also stops it after loss of creator proof. A code redeemed before a lost acknowledgement remains consumed. A new code starts a new empty inbox.

Each listener accepts at most 16 sockets and processes one request at a time per socket, with no application request queue. Ordinary frames bound requests at 16 KiB and responses at 4 MiB plus 4 KiB. Joining and writing have ten-second deadlines. The read idle deadline is one minute. Admitted sockets can send text, poll their live inbox and open a visible attachment's frozen description and bounded LaY captures. The wire projection omits EY identities until a recipient-side workspace can verify them. An admitted upload with an exact text and message-ID header can submit one follow-up frame of at most 2 MiB plus 32 KiB under the same request deadline. The host accepts only a description and up to two canonical RGB24 LaY captures. It validates their sizes, item shape and SHA-256, then uses the admitted sender and assigns the journal identities. The host cannot attest to a remote screen or seal. It accepts no guest EY, source paths, source IDs, attachment IDs or claimed provenance. The listener does not write a second journal or record an invitation in chat. Cross-device use still needs trusted certificate and invitation distribution and transport ownership across devices.

A same-network release needs an explicit reachable interface and authenticated host handoff, along with a compatible guest editor. A cross-network release also needs a reachability mechanism such as a relay or a managed private network. A relay brings operating, traffic and abuse-control costs. A private network can add guest setup and administration. Both need a trust path for the host credentials and one-use invite. Guest browser support would require a separate client path.

With `CONFECTORY_DEV_PUBLIC_CHAT_LOOPBACK=1`, a desktop EditorHome can issue from **로컬 채팅 초대** in the project title menu. **로컬 초대 참가** is available on Home and in that same menu. Copy the invitation directly between trusted windows on the same computer. It includes the loopback port, project ID, public TLS certificate and one-use code. It is selectable text, with no automatic clipboard write or browser URL. While the listener is active, the host's existing Chat shows a separate **공용으로 보내기** text form. An admitted guest sees the same control below the live list in the invitation chat window. The guest's local project and the existing Helper composer remain independent.

A disposable transient WebUI view owns each invitation window and skips the ordinary request replay cache. Each text submission clears on commit acknowledgement. A retry with unchanged text in the same view reuses its message ID, and the list shows only committed rows. A changed project scope, closed view or lost connection ends sending in that view. Closing the issuing window ends the listener, and closing the guest window ends its connection. The host can select its current sealed YogiBox with **봉인 YogiBox 첨부** or drop it onto the public composer. Both actions only prepare the attachment. **YogiBox 첨부 취소** clears the selection. **공용으로 보내기** commits the text and frozen attachment together. A failed write leaves both in the composer for retry. The host and currently admitted guests can open **YogiBox 보기** on the committed row. Guests can read the description and LaY captures within their current connection. Guest EY navigation still requires recipient-side authorization.

An admitted guest can prepare an attachment the same way from a sealed YogiBox in the locally open project. The native editor rechecks that project's identity, the owning window, connection, and exact seal when the guest explicitly sends. It refuses a box containing any EY and leaves the local box intact. The host's existing journal commits the public message and LaY together and neither editor adds a Helper record. Retrying within the same connection with the same message ID and content acknowledges the existing row. Closing the guest view or changing projects discards the selection. A new invitation starts with an empty inbox, including for a guest's own previously sent attachments.
