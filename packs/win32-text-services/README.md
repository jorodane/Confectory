# Windows x64 TextServices rendering proof

Public contract: Request(host, operation, payload, parentWindow) -> string. This explicit native pack retains an ITextHost/ITextServices pair created by Msftedit.dll CreateTextServices. It has no child RichEdit HWND and draws native text/selection through Window's public buffered canvas lease. It is **not a completed interactive input provider**; snapshot reports interactiveReady=false. Existing NativeUI desktop consumers remain unchanged.

Operations: create with text, bounds and optional readonly (default true), draw with surfaces/view/bounds/regions, snapshot, focus, pointer, send and close. Create borrows a live parent on its creating UI thread. Snapshot projects native WM_GETTEXT/EM_EXGETSEL and host-supplied caret geometry; it does not manually measure text or selection. Draw updates the native client/extent cache on movement, clips each published region, calls TxDraw into the same owned backbuffer and releases the canvas in finally. Native services and default formats persist between draws. Close is idempotent, UI-thread owned, and releases the service, callbacks, formats, measurement DC and module; it never closes the borrowed parent. No glyph/clipboard/shortcut/Hangul editing implementation is supplied.

Pointer forwards parent-client down/move/up packets after the consumer's common hit/capture decision. Focus invokes native UI activation; timers, capture callbacks, invalidation/cursor integration and full raw keyboard/IME routing are still passive placeholders. The proof consumer owns its Window capture and render cadence. Do not select this as an ordinary editable BaseUI NativeInput provider or infer OS keyboard/IME readiness from managed compilation. The raw send operation is a trusted native capability, not a user-text command interface. Coordinates/selection offsets are native UTF16/pixels, not the complete normalized BaseUI bridge contract.

The initial C++ vtable binding explicitly requires Windows x64, where the Windows x64 calling ABI is uniform. It rejects x86. Method ordering/signatures were checked against [Microsoft TextServ.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/TextServ.h) and [windowless RichEdit documentation](https://learn.microsoft.com/en-us/windows/win32/controls/about-windowless-rich-edit-controls). Engine composition owns background/border and visible regions; ITextHost requests transparent background and native layout supplies drawing/selection and caret geometry. Real font/layout/focus/IME/DPI correctness requires actual Windows checks.

Linux ABI fixture tests validate host slots/default formats, exported IID query/refcounts, retained independent objects, public-canvas DC/layout/clip consistency, moving layout, native selection projection, thread guards, late-use rejection, cleanup and provider locality. The fixture does not emulate actual RichEdit editing or prove Windows runtime behavior.

Experimental input bridge: input-begin/input-end install and retire a rooted parent HWND subclass on the creating UI thread. Focus explicitly sends WM_SETFOCUS/WM_KILLFOCUS plus native UI activation; only one service owns native focus for a parent. Raw keyboard/Unicode/IME/input-language messages go to TxSendMessage without reimplementing shortcuts. S_FALSE returns to the parent chain; other successful results return the native LRESULT. Tab/Escape remain parent navigation. Pointer forwarding still follows the consumer's common UIOrder hit/capture decision. External parent focus loss and WM_NCDESTROY retire activation/subclass ownership. Callback failures are caught at the unmanaged boundary and surfaced at the next request. inputAttached reports connection; interactiveReady stays false: timer/capture/cursor/caret rendering and IME geometry completion are still pending, and no actual Windows behavior is asserted. Existing NativeUI/Home is unchanged.
