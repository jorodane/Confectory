# RealTimeUpdate 0.1

Independent IDs: `Confectory.RealTimeUpdate::{CreateSchedule,Register,Unregister,Dispatch,IsRegistered,Advance,QueueCameraIntent,PresentCamera}`. All state is supplied by the consumer, with no static mutable fields or dependency on multiplayer/AI.

Schedule order is ascending phase-local priority, then registration sequence. Phase names are consumer-defined. Dispatch returns an ordered snapshot. Register during dispatch affects the next snapshot. Consumers check IsRegistered before each pending invocation so removal affects the current dispatch; replacing the same function/phase during a dispatch is currently forbidden by consumer policy. Consumers serialize dispatch and reject reentrancy, terminate the phase on callback failure, and report phase/function/priority/cause; callbacks are actual ID-bound imports in the ProjectPack, not reflection into providers. The scheduler plans calls; the consumer owns loop, thread, invocation and phase order.

`Advance(clock, elapsed, variablePeriod, renderPeriod, fixedPeriod, maximumSteps)` uses a three-slot opaque accumulator initialized to zero. Period zero means each pump for variable/render; fixedPeriod must be positive. Result is `[variableDue,renderDue,fixedSteps,interpolationAlpha,droppedSeconds,variableDelta,renderDelta,fixedDelta]`. Variable and render use independent elapsed accumulators and dispatch once with their accumulated delta. Fixed steps consume whole accumulated periods, capped by maximumSteps. Excess complete steps are deliberately dropped, returned as droppedSeconds for diagnostics; the fractional remainder is retained. This avoids unbounded catch-up after suspend/stall. This policy is pack-owned. Display interpolation alpha is the remainder fraction, not another simulation update. Reject invalid, nonfinite or overflowing time inputs before mutation.

Recommended consumer order: pump and queue input; fixed state updates; variable state update when due; camera intents; presentation snapshot; render/picking from the same snapshot when due. All camera intents are queued before one camera commit. This initial camera policy is 2D translation and scalar zoom, explicitly not a complete 3D projection contract. Queue starts `[0,0,1]`; camera starts `[x,y,zoom]`. PresentCamera applies all queued deltas/zoom and returns a fresh coherent frame snapshot. A subsequent input or presentation cannot change that previous snapshot. No camera policy is in the core or native adapter.

The example exercises independent cadences, priority ties, registration snapshots/removal, a stalled-frame overflow budget, mixed keyboard/drag/wheel/programmatic intents, and previous-frame snapshot isolation.
