# BaseUI 0.1

This first BaseUI slice supplies a reusable counter/boolean control panel outside any table. It is not a full editor or general declarative widget interpreter.

Public definitions: `Confectory.BaseUI::{ScalarSchema,BooleanSchema,Count,Toggle,CountView,ToggleView,ControlPanel,Controls}`. `ControlPanel` composes element Views and a role module; Count/Toggle are consumer-owned instance definitions. No table owns their model semantics. Metadata describes the currently implemented slice and participates in normal ProjectPack graph/catalog linking. Future text/collection/widget-slot semantics must extend explicit contracts, rather than silently treating these numeric arrays as a complete UI schema.

Independent function contracts: `CreateView`, `Layout`, `Input`, `UpdateView`, `Labels`, `ViewStatus`, `Invalidate`, `Presented`. Controls combines these functions and RuntimeBase's ScalarModels module, with explicit default implementation IDs. ProjectPack explicit bindings still take precedence. Render requests go through RenderInput's Draw contract; input arrives through Pump. BaseUI contains no OS APIs or provider class references.

CreateView returns persistent opaque View state. Consumers read a fresh public ViewStatus snapshot `[width,height,dirty,count,countRevision,toggle,toggleRevision,focus]`, request Invalidate, and acknowledge Presented; they never inspect or edit private state slots. Its five stable render slots are header, count, increment, enabled and camera. Layout uses supplied logical dimensions and recomputes geometry without reconstructing View/control instances. Input is the Controller: an inside press and inside release activates once; outside release, focus loss and pointer cancel release press state. Enter/Space repeat is suppressed and Tab changes focus. Pointer cancellation preserves independent keyboard press state. Toggle and counter actions request validated consumer model changes through RuntimeBase; changing supplied display properties does not echo input events.

Subscribe before Read when connecting. Each View subscribes only to its intended model instance and element. UpdateView validates before changing state and marks that View dirty. Unrelated Views and native windows are untouched. Closing a View releases subscriptions first, retaining the model Owner until session teardown; reopening reads the existing model and creates fresh subscriptions. Native/model/compiled-code lifetimes are separate. No live DLL reload or automatic schema migration is claimed.

The two-window engine sample preserves View state while closed (including logical dimensions/focus) and retains its model. A reopen makes only the removed native surface again. Android preserves models across pause/surface loss and saves scalar data through Activity configuration recreation; it presents two logical Views on one native surface, not two independent Android OS windows. Android native source remains unverified until its SDK/workload build and runtime check are completed.

Checkpoint 2 adds the reusable ProjectPanel element View and ProjectControls role module, with stable project/status/open/start/stop/close slots. CreateProjectView/ProjectLayout/ProjectInput/ProjectLabels accept public snapshots, without dependency on a manager implementation, table or engine host. ProjectInput returns 1 Open, 2 Start, 3 Stop, 4 Close, -1 consumed/cancelled pointer action, or 0 no action; the caller owns the actual capabilities. Keyboard O/S/T/C ignores repeat, pointer activation requires same-button release, and focus loss cancels. Errors render visibly from an explicit diagnostic snapshot. Closing the containing native View is independent of the project or execution lifetime.

Focus routing is now optional consumer composition: unconditional Tab interception has been removed from Input. Public Focus(query/set/disable/enable/hide/show) manages only basic control focus/eligibility; Activate requests one eligible model action. UINavigation owns configured traversal/groups/priorities/restoration without reading opaque Views. The engine explicitly binds its demo Tab behavior. Input still supports pointer and basic Enter/Space activation for compatibility; configured Navigation activation consumes the record before that fallback. See [Navigation contracts and configuration](../ui-navigation/README.md).

Generic control surfaces: CreateControls(positive unique IDs, up to128) returns a UI-thread-owned opaque token. ControlState(token, query/focus/cancel/show/hide/enable/disable, ID) returns `[focus,pressed,hover,eligibleIDs...]`; repeated same focus preserves capture, a changed focus cancels it. ControlInput accepts ID,x,y,width,height records, tests the topmost eligible rectangle, captures pointer-down and emits an ID only on matching pointer-up; resize/focus-loss/app-interrupt cancel capture. Hidden/disabled controls cannot receive input. CloseControls is idempotent and closes visual state only, never a workspace model. This additive contract leaves the earlier two-control Views unchanged. See Editor public consumer and locality tests.

## Shared Button

`Button(surface,control,bounds,label,palette,visible,enabled) -> string` is the reusable button. It updates visual availability on an existing control surface and produces a public frame with `id,visible,enabled,focus,pressed,hover,rectangles,labels,hit`. Bounds are x/y/width/height; palette is normal/hover/pressed/focus/disabled RGB backgrounds. Forward rectangles/labels to RenderInput::Draw and aggregate hit records for input. Presentation state/style selection and hit geometry are owned here; callers supply geometry/text/style and bind activation IDs to their domain actions. No Editor or model/table dependency exists.

`ButtonInput(surface,eventID,allControlHits,buttonIDs,type,x,y,activation) -> int` performs shared dispatch through ControlInput, filtering activation to registered eligible buttons. Monotonic event IDs prevent duplicate delivery. First call processes native pointer/focus/cancel events (activation0), then optional navigation may use the same event ID with type0 and a semantic press(-focusedID) or release(+focusedID). Only an armed matching release activates; repeats/duplicate phases cannot activate twice. Pointer capture, keyboard press styling, focus/availability changes, resize/focus-loss/app interruption and closed lifetime are handled in the pack. Keyboard bindings/navigation remain caller/Navigation policy, rather than OS-specific keys inside Button. Explicit screen/group transitions send cancellation type11 using a fresh event ID. CloseControls releases the surface's Button dispatch state too.

A real editor-free consumer `examples/button-game` uses these exact APIs and the existing RenderInput/Window/RuntimeBase/RealTimeUpdate/Navigation roles. It implements only its score actions and composition; it has no Editor/EditWorkspace/SourceEditor/ProjectManager dependency and no independent button drawing/hit implementation. Tests cover shared presentation, pointer/keyboard/duplicate/repeat/cancel, independent state, hidden/disabled, UI-thread/closed/recreated lifetime, native Linux and managed Windows/Android profiles. Provider-only edits to ButtonBody/ButtonInputBody rebuild only their implementation and0contracts.
