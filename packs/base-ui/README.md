# BaseUI 0.1

This first BaseUI slice supplies a reusable counter/boolean control panel outside any table. It is not a full editor or general declarative widget interpreter.

Public definitions: `Confectory.BaseUI::{ScalarSchema,BooleanSchema,Count,Toggle,CountView,ToggleView,ControlPanel,Controls}`. `ControlPanel` composes element Views and a role module; Count/Toggle are consumer-owned instance definitions. No table owns their model semantics. Metadata describes the currently implemented slice and participates in normal ProjectPack graph/catalog linking. Future text/collection/widget-slot semantics must extend explicit contracts, rather than silently treating these numeric arrays as a complete UI schema.

Independent function contracts: `CreateView`, `Layout`, `Input`, `UpdateView`, `Labels`, `ViewStatus`, `Invalidate`, `Presented`. Controls combines these functions and RuntimeBase's ScalarModels module, with explicit default implementation IDs. ProjectPack explicit bindings still take precedence. Render requests go through RenderInput's Draw contract; input arrives through Pump. BaseUI contains no OS APIs or provider class references.

CreateView returns persistent opaque View state. Consumers read a fresh public ViewStatus snapshot `[width,height,dirty,count,countRevision,toggle,toggleRevision,focus]`, request Invalidate, and acknowledge Presented; they never inspect or edit private state slots. Its five stable render slots are header, count, increment, enabled and camera. Layout uses supplied logical dimensions and recomputes geometry without reconstructing View/control instances. Input is the Controller: an inside press and inside release activates once; outside release, focus loss and pointer cancel release press state. Enter/Space repeat is suppressed and Tab changes focus. Pointer cancellation preserves independent keyboard press state. Toggle and counter actions request validated consumer model changes through RuntimeBase; changing supplied display properties does not echo input events.

Subscribe before Read when connecting. Each View subscribes only to its intended model instance and element. UpdateView validates before changing state and marks that View dirty. Unrelated Views and native windows are untouched. Closing a View releases subscriptions first, retaining the model Owner until session teardown; reopening reads the existing model and creates fresh subscriptions. Native/model/compiled-code lifetimes are separate. No live DLL reload or automatic schema migration is claimed.

The two-window engine sample preserves View state while closed (including logical dimensions/focus) and retains its model. A reopen makes only the removed native surface again. Android preserves models across pause/surface loss and saves scalar data through Activity configuration recreation; it presents two logical Views on one native surface, not two independent Android OS windows. Android native source remains unverified until its SDK/workload build and runtime check are completed.
