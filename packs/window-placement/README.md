# WindowPlacement 0.1

Public contracts: `Create() -> string`, `Update(state, operation, payload) -> string`. This common geometry role has no UIOrder, native surface, Owner, editor, timer, render or input dependency. Values are immutable JSON; failed updates leave the caller's old value intact. A desktop editing View or Android app-surface pane may consume the same geometry contract without pretending their operating-system windows have identical capabilities.

State has `area` and `items`, keyed by caller-owned stable strings. An item stores displayed `bounds`, unconstrained `intent` bounds, local draggable handle, minimum visible handle extent, live/suspended flags and optional anchor `{target, point:[x,y], pivot:[x,y]}`. `target` is `viewport` or another stable key, never a UI parent or live object/handle. IDs must be stable for the semantic window: reopening the same key means reappearance; a different semantic window needs a different key. At most 64 identities per scene, bounded coordinates/dimensions and serialized state budgets. Closing a scene discards the value; retained missing identities require a new scene after the identity budget is exhausted, rather than silently losing suspended relations.

Operations:

- `viewport`: `{bounds:[x,y,w,h]}`. Apply stored relationships using current geometry, then reachability; never choose a new anchor. Zero viewport is rejected; suspend updates and retain the last live viewport during surface loss.
- `open`: `{key,bounds,handle:[x,y,w,h],minimum:[w,h]}`. Introduce or reappear with the same stable identity; preserve existing anchor intent, fresh caller-owned native lifetime. Bounds and local handle must be valid.
- `geometry`: `{key,bounds,handle?,minimum?}`. Programmatic position, resize, body fold/expand or restore. Preserve existing anchor/pivot; contact never creates one. If the supplied x/y equal current displayed x/y, retain intended x/y while updating dimensions, so measured layout/fold at a safety position cannot consume recovery. A changed programmatic x/y establishes new intended coordinates. A fold must update handle geometry if needed to keep it within the new bounds. This is distinct from native minimize or close.
- `move`: `{key,bounds}`. A user position gesture, with unchanged dimensions. Only the directly manipulated window changes position. Its former transitive dependents (including hidden identities) first retire old anchor/contact/suspension state, retain their current bounds as new independent intent, then live dependents rebuild valid relationships at those same coordinates. The common classifier retains the8-unit candidate policy, but stationary reconstruction accepts only exact contact/alignment that requires no coordinate correction; it does not magnetically move an ungrabbed window. Ordinal bounded passes permit a chain to rebuild regardless of key order. Remaining unrelated windows retain their existing intent. Reachability stops the window at a viewport boundary. Boundary contact establishes anchor/pivot; inward movement beyond the proximity band clears it. A symmetric 8-client-coordinate-pixel band around opposing edges, or crossing an edge from a positive gap, with orthogonal overlap and an already live anchored reference, establishes a relative relationship. Snap corrects the actual bounds to the exact reference edge, including shallow penetration. Corresponding top/top, bottom/bottom, left/left and right/right edges align in the same 8-unit band, alongside adjacency or independently while retaining arbitrary offsets on the other axis. Eligible adjacency precedes matching-edge alignment, then viewport fallback. Candidate ties use ordinal stable key order, nearest eligible edge within one candidate and deterministic vertical/leading ties. Moving beyond the band detaches that axis; another qualifying alignment may remain. No docking, automatic container conversion or unsolicited packing is implemented.
- `availability`: `{key,live}`. Hide/minimize and reappearance without deleting identity. `remove`: `{key}` marks an identity absent. Both leave only geometry/identity values, no native or Owner resources.

For a window that fits an axis, the complete body stays inside that viewport axis. Corners use equal anchor/pivot corners. Right-only uses point `[1,top/viewportHeight]`, pivot `[1,0]`; left-only is symmetric. Top-only retains proportional left position and top-left pivot; bottom-only retains proportional left position and bottom-left pivot. Bottom contact therefore holds the bottom edge during a height reduction and moves the title downward; right-only holds the title top. Projection rounds once, away from zero; fractions are retained across resize rather than recomputed from rounded pixels. Window resize/fold and viewport resize preserve the relationship, even when effective safety geometry temporarily differs.

An oversized axis cannot satisfy full-body containment. It instead preserves the declared minimum visible title handle, capped by the available viewport/handle extent, without resizing the window or inventing an anchor on that axis. Reachability is also the final safety constraint on relative anchors; a viewport too small for a connected group may prevent exact physical edge contact while keeping the stored relationship. Returning to sufficient space reapplies it. Free placement keeps intended coordinates separately from clamped displayed bounds, so partial recovery approaches the original position and full recovery restores it without accumulated drift. A direct move cancels the old intent and stores the new snapped/safe position; repeated layout, activation, restore and geometry at unchanged displayed coordinates do not cancel it. Older serialized state lacking intent initializes it from its available bounds; coordinates already lost by older versions cannot be reconstructed. This bounded fallback is not a layout solver.

Adjacent windows attach using the contacted target edge and the matching own pivot (below target: target bottom / own top; above: target top / own bottom; right: target right / own left; left: target left / own right). The other coordinate is a proportional offset in the reference bounds. Reference programmatic geometry/resize/fold updates connected windows in dependency order. Direct reference dragging instead leaves them stationary and rebuilds relationships, so old offsets cannot reapply after release or on later frames. If the reference disappears, the child holds its current position, except necessary viewport reachability recovery, and suspends its relationship; untouched children resnap on the same stable key's return. A direct user move while suspended clears that relation. Missing-reference chains suspend transitively. Self-reference and cycles are rejected, including serialized dormant cycles. Reappearance does not resurrect old native objects.

`examples/ui-order-game` validates this public contract independently of editor/native resources, including corner/fractional anchors, detach, resize without attachment, fold/expand, relative chains, suspension/reappearance, movement during absence, cycle rejection, tiny/oversized geometry, repeated layout and separate UIOrder focus/order locality. No consumer body-fold button is provided by this milestone: fold semantics are tested through geometry updates. No actual Android app/native lifecycle or Windows compositor acceptance is implied by these headless tests.

Transient `contact:{target,edges:[...],targetEdges?:[...]}` reports only the actual chosen contact from the anchor classifier. Edges are the moving window’s left/top/right/bottom; corners contain two. Leaving contact, geometry/viewport changes or unavailable references clear it. `targetEdges` maps each marked own edge to the reference edge (indices left0/top1/right2/bottom3, unmarked -1), distinguishing adjacent contact from corresponding-line alignment. Older metadata without a mapping retains opposed-edge interpretation. Final safety projection removes any indicated edge whose resulting coordinate differs from the chosen target line, while retaining anchor intent. This is presentation data, not a proximity preview.

The previous ae976e6 implementation had a **0-unit proximity band**, exact contact plus crossing; there was no positive numeric distance to double. This increment adds **0→8 client-coordinate pixels**, selected as an implementation starting value, not a user-specified number or a literal 2× change. These are the coordinates supplied by the consumer/render/input adapter, not guaranteed physical screen pixels or DPI-independent units. No native DPI conversion was changed. Viewport boundaries also snap within8 units. Crossing from a positive gap still catches skipped pointer samples; leaving an existing contact beyond8 does not recreate that adjacent relation.

Single-window gesture gates additionally cover branched dependencies, reverse-key chains, middle-node dragging, repeated attach/detach, post-release layout, hidden descendant retirement and unchanged automatic fold/viewport/reappearance behavior. The actual X11 probe drags an anchored reference back/forth four times while asserting its connected pane remains stationary during movement, release and subsequent idle frames.
