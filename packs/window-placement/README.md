# WindowPlacement 0.1

Public contracts: `Create() -> string`, `Update(state, operation, payload) -> string`. This common geometry role has no UIOrder, native surface, Owner, editor, timer, render or input dependency. Values are immutable JSON; failed updates leave the caller's old value intact. A desktop editing View or Android app-surface pane may consume the same geometry contract without pretending their operating-system windows have identical capabilities.

State has `area` and `items`, keyed by caller-owned stable strings. An item stores bounds, local draggable handle, minimum visible handle extent, live/suspended flags and optional anchor `{target, point:[x,y], pivot:[x,y]}`. `target` is `viewport` or another stable key, never a UI parent or live object/handle. IDs must be stable for the semantic window: reopening the same key means reappearance; a different semantic window needs a different key. At most 64 identities per scene, bounded coordinates/dimensions and serialized state budgets. Closing a scene discards the value; retained missing identities require a new scene after the identity budget is exhausted, rather than silently losing suspended relations.

Operations:

- `viewport`: `{bounds:[x,y,w,h]}`. Apply stored relationships using current geometry, then reachability; never choose a new anchor. Zero viewport is rejected; suspend updates and retain the last live viewport during surface loss.
- `open`: `{key,bounds,handle:[x,y,w,h],minimum:[w,h]}`. Introduce or reappear with the same stable identity; preserve existing anchor intent, fresh caller-owned native lifetime. Bounds and local handle must be valid.
- `geometry`: `{key,bounds,handle?,minimum?}`. Programmatic position, resize, body fold/expand or restore. Preserve existing anchor/pivot; contact never creates one. A fold must update handle geometry if needed to keep it within the new bounds. This is distinct from native minimize or close.
- `move`: `{key,bounds}`. A user position gesture, with unchanged dimensions. Reachability stops the window at a viewport boundary. Boundary contact establishes anchor/pivot; inward movement clears it. Exact edge contact or crossing an edge from a positive gap, with orthogonal overlap and an already live anchored reference, establishes a relative relationship. Eligible relative contact precedes coincident viewport contact; candidate ties use ordinal stable key order. Moving from an existing contact into overlap detaches. No proximity threshold, docking, automatic container conversion or unsolicited packing is implemented.
- `availability`: `{key,live}`. Hide/minimize and reappearance without deleting identity. `remove`: `{key}` marks an identity absent. Both leave only geometry/identity values, no native or Owner resources.

For a window that fits an axis, the complete body stays inside that viewport axis. Corners use equal anchor/pivot corners. Right-only uses point `[1,top/viewportHeight]`, pivot `[1,0]`; left-only is symmetric. Top-only retains proportional left position and top-left pivot; bottom-only retains proportional left position and bottom-left pivot. Bottom contact therefore holds the bottom edge during a height reduction and moves the title downward; right-only holds the title top. Projection rounds once, away from zero; fractions are retained across resize rather than recomputed from rounded pixels. Window resize/fold and viewport resize preserve the relationship, even when effective safety geometry temporarily differs.

An oversized axis cannot satisfy full-body containment. It instead preserves the declared minimum visible title handle, capped by the available viewport/handle extent, without resizing the window or inventing an anchor on that axis. Reachability is also the final safety constraint on relative anchors; a viewport too small for a connected group may prevent exact physical edge contact while keeping the stored relationship. Returning to sufficient space reapplies it. This bounded fallback is not a layout solver.

Adjacent windows attach using the contacted target edge and the matching own pivot (below target: target bottom / own top; above: target top / own bottom; right: target right / own left; left: target left / own right). The other coordinate is a proportional offset in the reference bounds. Reference resize/fold updates connected windows in dependency order. If the reference disappears, the child holds its current position, except necessary viewport reachability recovery, and suspends its relationship; untouched children resnap on the same stable key's return. A direct user move while suspended clears that relation. Missing-reference chains suspend transitively. Self-reference and cycles are rejected, including serialized dormant cycles. Reappearance does not resurrect old native objects.

`examples/ui-order-game` validates this public contract independently of editor/native resources, including corner/fractional anchors, detach, resize without attachment, fold/expand, relative chains, suspension/reappearance, movement during absence, cycle rejection, tiny/oversized geometry, repeated layout and separate UIOrder focus/order locality. No consumer body-fold button is provided by this milestone: fold semantics are tested through geometry updates. No actual Android app/native lifecycle or Windows compositor acceptance is implied by these headless tests.

Transient `contact:{target,edges:[...]}` reports only the actual chosen contact from the anchor classifier. Edges are the moving window’s left/top/right/bottom; corners contain two. Leaving contact, geometry/viewport changes or unavailable references clear it. Final safety projection clears feedback if physical contact is no longer possible, while retaining anchor intent. This is presentation data, not a proximity preview.
