CPU samples during the external GTK-only probe include Pango text measurement and GTK tree-view cell sizing beneath `gtk_entry_completion_complete` and `gtk_main_iteration_do`. The source of this path was inspected in GNOME's gtk-3-24 [entry completion](https://github.com/GNOME/gtk/blob/gtk-3-24/gtk/gtkentrycompletion.c) and [file chooser entry](https://github.com/GNOME/gtk/blob/gtk-3-24/gtk/gtkfilechooserentry.c). Popup sizing forces tree-view preferred-size validation. This is an observed latency candidate, **not a proven cause of the historical failure**. Profiling itself is supplementary and is not counted as an unchanged functional gate. A private fixed-cell-size experiment did not establish improvement and was not adopted. The new diagnostic recorded single GTK iterations of approximately 0.45 and 0.92 seconds in early runs; these are not ten-second failures.

The key snapshots are dialog-level observations, not a complete delivery trace: GTK completion's popup handler forwards events directly to the entry (`gtk_entry_completion_popup_key_event`), bypassing the dialog callback. Missing dialog callbacks or long gaps between those callbacks therefore cannot establish dropped input or event-loop latency. Use the measured individual GTK iterations for the latter; a future failing trace should additionally observe the focused entry's events.
