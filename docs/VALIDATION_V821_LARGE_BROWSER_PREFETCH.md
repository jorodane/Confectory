# 대규모 프로젝트 Browser 복원 성능 검증

기준: `c72d8965df7c5eb7a421073e966a4360608dcdbd` (`work/current`). Linux x64, .NET SDK 10.0.401, 실제 EditorHome 호스트와 Chromium. Windows 실제 WebView2/기기 검증은 이번에 하지 않았다.

## 채택한 변경

등록 인벤토리가 `available`이고 실제 소유 object 선언이 128개를 초과하면 Browser의 선택적인 `preparePropertyModels` 사전 조회를 시작하지 않는다. 인벤토리의 각 소유 object ID는 해당 선언 파일과 일치하는지 확인되므로, 이 수의 서로 다른 선언은 기존 완전한 소유권 경로 증명 상한인 128을 이미 넘는다. 이 조회는 어차피 모델을 게시하지 못하고 일반 명령·검색과 동일한 호스트 전송 경로를 사용했다.

작업 중 프로젝트·활성화·창 및 최신성 확인은 유지한다. 인벤토리가 확인되지 않았거나 작은 경우 기존 사전 조회와 재시도를 유지한다. 명시적인 속성 창 열기, 복원 상태 증명, 모델 증명 상한, 실제 소스/소유권 검증 및 Run은 바꾸지 않았다. 외부 변경 이후에도 실제 열기는 기존 검증 경로에 의존한다.

### 실제 복원 측정

`tests/run_isolated_browser_test.py -- python tests/web/v821_workspace_restore_performance.py REPO BUILD_REPORT WINDOW_COUNT --exercise-command`를 사용했다. 환경변수 `CONFECTORY_RESTORE_OBJECTS=40|400`으로 각 규모를 선택했다. 실제 Home 카드 클릭부터 첫 편집 가능, 마지막 편집 가능, 일반 명령 활성화 및 실제 Browser 메뉴/분류 선택/검색 결과 확인까지의 밀리초다. Warm은 같은 호스트에서 재진입, cold는 호스트와 브라우저 페이지를 다시 시작한 복원이다. 400개·8창은 각 후보와 기준선을 3회씩 측정한 중앙값, 나머지는 각 1회다. Home 요약 완료 후 시작했으며, 단일 측정의 변동이나 Playwright의 실제 UI 탐색 시간도 포함한다.

400개·8창에서 `preparePropertyModels` 호출 수는 warm 4 → 0, cold 3 → 1이었다(각각 세 번 모두 동일). cold의 1회는 기존 실제 복원 상태 증명 요청이다. 검색 완료 warm 표본은 기준선 1373/1449/1480 ms, 후보 1301/1336/1352 ms였다. cold는 기준선 2589/2697/2725 ms, 후보 2555/2592/2721 ms다. 실제 Browser 표시부터 분류 선택 및 검색 결과 확인까지의 3회 중앙값도 warm 499 → 415 ms, cold 381 → 349 ms였다. 일반 명령 준비와 첫/마지막 편집 가능 시간이 일관되게 개선되었다고 판단하지 않는다. 다른 단일 표본 조합도 개선을 보증하지 않는다.

## 제외한 후보와 다음 병목

- Browser 인벤토리/저장 필터 100ms 폴링을 `whenIdle()`/`whenReady()`로 바꾸는 후보는 전체 6조합 및 저장 작업 사본 필터를 확인했지만 일관된 검색/명령 개선이 없어서 제외했다.
- 변경 없는 폴더 트리 재생성을 생략하는 후보 역시 전체 경로에서 이득이 일관되지 않아 제외했다.
- 인벤토리 전용 선언 직접 읽기는 실제 400개 소유 프로젝트 스트림 반복에서 동일 의미 출력(읽기 통계 제외)으로 약 142–151 → 71–79 ms의 따뜻한 조회 중앙값을 보였다. 호스트 cold 인벤토리 소비 시간(3회 중앙값) 296 → 247 ms였으나 전체 검색 결과 개선은 작았고 사전 조회 제거와 조합해도 cold 결과가 좋아지지 않아 제외했다. 기존 선언 영속 캐시는 그대로 유지했다.
- 실제 cold 경로에는 복원 `preparePropertyModels` 1회, `openEditorView` 3회 및 `localInventory`/`relationsMap`이 남는다. 400개 기준선의 Chromium CPU 분리 프로파일은 약 3.05초 중 샘플상 idle 약 1.85초였다. 즉, 단순 DOM 최적화보다 호스트/전송 대기 및 전체 소유권 증명 구조가 다음 대상이다. 기존 128경로 제한 때문에 모델 게시가 거절되어 실제 창별 열기를 수행한다. 한도를 무작정 늘리거나 최신성 검증을 생략하지 않았다. 큰 프로젝트의 전체 소유권 증명을 효율적으로 검증하고 창 복원 단계의 중복 상태 전달을 줄이는 것이 다음 작업이다.

## 보호 동작 검증 (채택 후보)

모두 실제 Linux EditorHome 호스트 및 Chromium 151.0.7922.173에서 격리 실행기를 사용했다. 테스트 프로젝트와 프로필은 매번 합성 임시 사본이었다.

- `v821_project_browser_search_labels.py`: 동일 표시 이름/다른 탭, 범주·모듈, 외부 이름 변경, 트리 포커스·스크롤·캐럿, 동일 namespace를 가진 두 프로젝트 격리 통과.
- `v821_property_window_reopen_ui.py`: 미저장·저장 초안 유지, 호스트 상태 읽기 대기 중 입력, 62.5% 확대 상태에서 실제 포인터 복원, 재시작 후 입력 유지 통과.
- `v821_workspace_restore_status_ui.py primary-external-during`: 준비 중 외부 스키마 변경으로 기존 primary 상태 증명이 무효화되고, 새 스키마와 정확한 3개 소유자 및 입력을 복원함.
- `v821_workspace_restore_status_ui.py primary-close-persist`: 복원 완료 후 명시적 닫힘 유지, 재시작 후 닫힌 레이아웃 보존 및 명시적 열기 시 입력 복구.
- `project_string_property_save_ui.py 400 --trace-files --guards`: Unicode 문자열, 독립 창 빈 문자열, 정수 저장 및 재시작, 읽기 불가/외부 소스 변경의 거절과 입력 유지. 컴파일러 실행 0, 프로젝트 DLL open 0.
- `v821_reference_data_run_ui.py 400 --detached`: 참조 선택 및 저장 전후 컴파일러 0, 프로젝트 DLL open 0. 명시적 Run에서 실제 연결된 새 값을 읽어 종료 코드 0, 컴파일러 실행 7, 프로젝트 DLL open 84.

모든 완료된 위 격리 테스트에서 테스트 소유 잔류 자식 프로세스 0이었다. 환경 초기 Git fetch 이후 PID 1에 남은 Git zombie 하나는 별도로 관찰되었으며 브라우저/호스트 테스트 잔류 프로세스는 아니다.

### 저장 작업 사본 필터와 지도 재조회 복합 경로

`--working-copy`는 재진입 측정 후 실제 작업 사본 검색을 다시 저장하여 재시작에서도 동일 모드를 검증한다. 저장 필터 입력과 정확한 결과가 실제 Browser에 복원되는지 별도 확인한다. 필터 검증과 지도 재조회 검증은 각각 독립 실행한다.

추가 복합 검증(`--working-copy --verify-restored-map`)은 기준선과 채택 후보 모두 저장 필터·결과 복원에 성공했지만, 외부 스키마 편집 후 명시적 `relationsMap` 호출이 끝난 뒤 primary 속성 창에서 `MapReloadProbe` 필드가 보이지 않아 실패했다. 독립 속성 창에는 새 필드가 나타났으며, 기준선에서도 동일한 현상이므로 이번 사전 조회 제거의 회귀로 보지 않는다. 이 복합 경로의 primary 표시 갱신은 미해결이다. 기존 `primary-external-during`, 외부 원본 변경 저장 거절, 일반 지도 갱신은 별도로 통과했으며 이 실패를 통과로 계산하지 않았다. 두 복합 실패 실행 또한 테스트 소유 잔류 자식은 0이었다.

수정된 작업 사본 필터 단독 검사에서 기준선·폴링 후보·채택 후보 모두 warm/cold의 저장된 검색어 및 정확한 결과 확인을 통과했다. 단일 표본의 명령/검색 완료 시간은 다음과 같다.

| 구분 | 기준선 명령/검색 | 완료 신호 폴링 후보 | 채택 후보 |
|---|---:|---:|---:|
| warm | 981 / 1591 ms | 1075 / 1772 ms | 1010 / 1627 ms |
| cold | 2524 / 3424 ms | 2307 / 3414 ms | 2329 / 3237 ms |

이 단독 측정에서도 완료 신호 후보를 채택할 만큼 전체 검색이 일관되게 개선되지 않았다. 저장 필터 cold의 일반 명령 지연은 별도 최적화 대상이다.

총 성능/회귀 격리 실행 58회 중 56회 통과, 위 복합 경로 실패 2회(기준선/후보 각 1회), 테스트 소유 잔류 자식 합계 0이었다. 별도 Chromium 시작·종료 단독 프로브도 통과했다.
