# v480 local Run frame control

This increment connects the existing Run viewport to a cooperative desktop runtime. The frozen v480 `openRunViewport` has Play, Pause and Step, but explicitly calls its execution MOCK and increments a private demo `runFrame`. None of that demo state establishes execution, frame completion or Stop authority. Existing ProjectExecution session/handle ownership and build/run/owned-tree Stop remain authoritative.

## Ownership and protocol

`ProjectExecution::Control(session,handle,operation)` accepts `observe`, `pause`, `resume`, `step`, `disconnect` and `reconnect` for exactly the caller's owned launch record. Each desktop LaunchConfigured creates a new random pipe name, 256-bit secret and existing execution handle. Reserved `CONFECTORY_FRAME_*` configuration cannot replace that identity; nested launches receive new identities. No PID scan, stdout command interpretation, HTTP service, remote bind, account or permission expansion is introduced. The local .NET named pipe uses current-user-only access and additionally checks the launch secret and handle. It is a capability boundary between trusted local projects, not an isolation sandbox for hostile same-user code.

Requests and replies are length-prefixed strict UTF-8 JSON, bounded to 4096 bytes, version 1. The client has one serialized request with a fresh request nonce; the runtime has a fresh runtime epoch. Parent validation checks handle, epoch, request nonce, nondecreasing completed frame and acknowledgement, acknowledgement no newer than the sent command, valid pending sequence and mode. Foreign/stale/future replies, non-object/null envelopes, missing fields and invalid numeric payloads never replace the last verified receipt or its pending-command fence. A malformed runtime request retires only that pipe connection; the owner remains available. Diagnostics/output are separate bounded execution logs, never a protocol transport.

Only one changing command may await acknowledgement. Its positive sequence follows the last acknowledged sequence. Exact retries of the current or last acknowledged command are idempotent; older, skipped, conflicting and concurrent command sequences are refused. A disconnected or uncertain command is never automatically replayed. An ordered fresh observation can establish that a failed send was never accepted, allowing a new explicit command. UI actions additionally carry the displayed execution handle, runtime epoch, acknowledgement and sent sequence; stale Step/Stop cannot affect a later Run. Existing WebView project scope/revision checks still apply.

## Real frame boundary

The independent `Confectory.FrameControl` pack exposes `Open`, `Begin`, `Complete` and `Close`. It contains no editor, game state, Core compiler or native window ownership. The creating loop thread calls Begin and receives 0 (paused), 1 (ordinary frame) or 2 (one requested fixed frame). Complete is permitted exactly once after actual callbacks and presentation finish. A transport-accepted Step remains pending until Complete; failure, Stop or Close during callbacks creates no completed frame or successful Step acknowledgement. Reentrant Begin, fabricated Complete and wrong-thread callbacks are rejected.

Pause is acknowledged at a boundary after the previous frame completes. Resume is acknowledged when the boundary accepts ordinary scheduling. Step requires a paused owner, performs one fixed update plus variable/presentation work with the consumer's declared fixed delta, and remains paused. Accumulators are cleared across pause/Step to avoid a suspend catch-up burst. The frame is a completed consumer scheduler iteration; it is not an invented FPS, an OS signal or a claim that a child render surface is embedded in the Run window.

A two-second observation heartbeat lease makes an unobserved runtime pause at its next cooperative boundary. It cannot interrupt a callback that never returns. A reconnect during a long callback still preserves the missed lease and pauses the next boundary. Reconnection queries the same live capability and epoch; it neither resumes a paused owner nor replays a command. Explicit disconnect suspends client transport/heartbeat; its last displayed frame is only the last verified observation. Existing Stop can terminate the owned process tree even when frame callbacks or transport are unresponsive.

## Consumers and limits

- Existing desktop Engine loop: input/close pumping remains live while simulation is paused; fixed/state/camera/presentation callbacks stop. Step forces one fixed update and actual presentation. Ordinary running cadence remains the existing RealTimeUpdate policy. Optional `CONFECTORY_ENGINE_TRACE_FRAME=1` records completed pipeline frames and fixed ticks for actual-runtime evidence.
- Existing ButtonGame desktop GUI loop: its actual native draw is the completion boundary, including a forced single draw for Step. Its headless widget self-check and browser route do not claim cooperative control.
- Ordinary `examples/frame-loop`: a local headless .NET simulation using declared RealTimeUpdate cadence and a real ID-bound Tick function. `LOCAL_FRAME` output records its completed model updates; it is not an embedded game/render demo. Its portable/linux/windows declarations permit local CLI and Run inspection without native-window requirements. Verify manifests are separate from its ordinary entry.
- Desktop ProjectExecution advertises the ability to contact a cooperative runtime, not that every ProjectPack supports frames. Nonparticipating projects retain ordinary Run/Stop and disabled Pause/Step. Android and independent browser/WASM process launch remain unavailable. No Android settings, workloads or device behavior changed.
- Browser reload and private-window close/reopen/hide retain the same live host owner. A new/cold host cannot adopt the previous pipe, secret or process. Durable launch recovery/rebinding, remote control, embedded surfaces/input routing, native Windows/device acceptance, export/deployment and user PC installation remain outside this increment. A previous surviving cooperative child may lease-pause, but the new host neither claims nor stops it.
- Property set/ref, extended ABI and general numeric overflow semantics remain separate unresolved work. Run does not Apply/Save/Confirm pending source inputs, change source permission or call an AI/provider.
