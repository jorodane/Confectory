# 복합 기능 저장·빌드 지연 조사

기준은 `018a4c0`의 실제 Linux Chromium 편집기이며, 합성 FrameLoop 프로젝트에 새 기능, 복합 내부 셀, case와 다른 기능 호출을 작성하는 기존 `tests/web/v821_new_function_document_ui.py full-clean` 경로를 사용했다. 실제 사용자 프로젝트나 계정은 사용하지 않았다.

## 호스트 경로

- Save의 하나의 authorBatch 호출 내부에서 `blueprintDescribeOwned`가 70회 호출된다. 세 정상 실행에서 이 합계는 1,251–1,456ms였다. 별도 프로세스로 수행하던 node-flow, enum 및 call 준비 합계는 639–740ms였다. 나머지는 실제 노드 소스, 캡처 및 계약 확인, checkpoint 작업이다.
- 후보는 기존 프로젝트별 상주 도구의 읽기 스트림을 준비 작업에도 적용한다. 소스/계약 결과를 캐시하지 않고 작업마다 그대로 계산한다. 새 프로토콜을 지원하지 않는 설치는 기존 개별 프로세스로 돌아가며, node-flow 내부 owner와 스트림 owner가 다르면 거절한다.
- Confirm은 정상 UI 관측에서 약 5.3초의 validate 호출과 약 0.2초의 나머지 호스트 작업을 포함한다. 이전 상세 trace에서 전체 소유 구현 Check 약 1.85초, 도달 구현 Build/Link 약 3.05초였다. 둘은 다른 계약이다: 사용되지 않는 잘못된 소스까지 거절하는 전체 Check와 실제 실행에 필요한 것만 남기는 Build. `tests/Confectory.Tests/VerificationTests.cs`는 서로 다른 산출물과 계약 범위를 요구한다. 단순히 한쪽을 삭제하거나 전체 Check 산출물을 링크하는 것은 적합하지 않다.
- Run 버튼의 명령 자체는 9–15ms이나 비동기 실행 호스트에서 새 빌드를 시작한다. execve 계측에서 Run 한 번에 실제 C# 컴파일러가 세 차례 시작되고 최종 프로그램 실행이 이어졌다. 전체 워크플로의 C# 컴파일러 시작은 15회였다. strace 자체의 큰 지연 때문에 해당 실행의 벽시계 수치는 정상 UI 비교에는 사용하지 않았다.
- 정상 UI와 호스트 합산의 차이를 전부 폴링으로 간주할 수 없다. 후속 상태 요청, 브라우저 렌더링 및 테스트의 표시 관측까지 포함된다. 폴링만 제거하면 전체 시간이 줄어든다는 증거는 없다.

## 다음 구조적 경계

동일 authorBatch 내 70회 graph projection을 줄이려면 변경된 frame과 계약/소스 관측을 하나의 명시적 트랜잭션 모델로 관리해야 한다. 독립 환경에 걸쳐 전체 Registry를 무조건 캐시하거나 변경된 원본의 검사를 생략하지 않는다. 별도로 빌드 도구 및 C# 프로세스 재사용을 검토하려면 정확한 SDK·컴파일러·타깃 입력 및 진단 의미를 보존하는 프로토콜이 필요하다. 전체 Check 및 도달 Build의 범위 차이와 원본/툴 변경 검사는 그대로 남는다.

## 반복 비교

| 측정 (ms) | 기준 3회 | 후보 3회 |
|---|---|---|
| 실제 복합 전환 클릭 → 편집 가능 | 909, 997, 1022 | 396, 290, 297 |
| 준비 작업 호스트 합계 | 639, 653, 740 | 171, 172, 262 |
| authorBatch 호스트 처리 | 3585, 3220, 3228 | 2760, 2629, 3120 |
| 실제 Save 완료 | 5999, 5386, 5389 | 5393, 4946, 5387 |
| 실제 Confirm 완료 | 6461, 5980, 5951 | 6456, 6471, 6461 |
| Run → 실제 출력 | 4342, 4735, 4791 | 4854, 5130, 4525 |

후보를 검증한 뒤 동일 환경에서 기준을 다시 실행하니 전환 954ms, 준비 661ms, authorBatch 3408ms, Save 5971ms, Confirm 6445ms, Run 4345ms였다. 핵심 호스트 작업과 실제 편집 응답의 개선은 반복되었지만, Save UI 중앙값은 거의 그대로이며 Confirm과 Run의 개선은 입증되지 않았다. 따라서 저장 성능 문제 전체의 해결로 간주하지 않는다.

실제 Chromium 정상 3회와 충돌 시나리오 1회, 상주 스트림 프로토콜 회귀를 통과했다. 합성 두 프로젝트의 원본 격리, 외부 그래프 및 donor 계약 변경 감지, 체크포인트 저장 충돌/Confirm 충돌 보호, 원본 C# 보존, 하나의 최종 Save/Confirm, 묶음 Undo/Redo, cold 재개방, 실제 새 기능의 세 실행 분기를 확인했다. Windows 실기는 검증하지 않았다.
