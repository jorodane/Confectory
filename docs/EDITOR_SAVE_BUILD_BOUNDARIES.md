# 복합 기능 저장·빌드 지연 조사

기준은 `018a4c0`의 실제 Linux Chromium 편집기이며, 합성 FrameLoop 프로젝트에 새 기능, 복합 내부 셀, case와 다른 기능 호출을 작성하는 기존 `tests/web/v821_new_function_document_ui.py full-clean` 경로를 사용했다. 실제 사용자 프로젝트나 계정은 사용하지 않았다.

## 호스트 경로

- Save의 하나의 authorBatch 호출 내부에서 `blueprintDescribeOwned`가 70회 호출된다. 세 정상 실행에서 이 합계는 1,251–1,456ms였다. 별도 프로세스로 수행하던 node-flow, enum 및 call 준비 합계는 639–740ms였다. 나머지는 실제 노드 소스, 캡처 및 계약 확인, checkpoint 작업이다.
- 후보는 기존 프로젝트별 상주 도구의 읽기 스트림을 준비 작업에도 적용한다. 소스/계약 결과를 캐시하지 않고 작업마다 그대로 계산한다. 새 프로토콜을 지원하지 않는 설치는 기존 개별 프로세스로 돌아가며, node-flow 내부 owner와 스트림 owner가 다르면 거절한다.
- Confirm은 정상 UI 관측에서 약 5.3초의 validate 호출과 약 0.2초의 나머지 호스트 작업을 포함한다. 이전 상세 trace에서 전체 소유 구현 Check 약 1.85초, 도달 구현 Build/Link 약 3.05초였다. 둘은 다른 계약이다: 사용되지 않는 잘못된 소스까지 거절하는 전체 Check와 실제 실행에 필요한 것만 남기는 Build. `tests/Confectory.Tests/VerificationTests.cs`는 서로 다른 산출물과 계약 범위를 요구한다. 단순히 한쪽을 삭제하거나 전체 Check 산출물을 링크하는 것은 적합하지 않다.
- Run 버튼의 명령 자체는 9–15ms이나 비동기 실행 호스트에서 새 빌드를 시작한다. execve 계측에서 Run 한 번에 실제 C# 컴파일러가 세 차례 시작되고 최종 프로그램 실행이 이어졌다. 전체 워크플로의 C# 컴파일러 시작은 15회였다. strace 자체의 큰 지연 때문에 해당 실행의 벽시계 수치는 정상 UI 비교에는 사용하지 않았다.
- 정상 UI와 호스트 합산의 차이를 전부 폴링으로 간주할 수 없다. 후속 상태 요청, 브라우저 렌더링 및 테스트의 표시 관측까지 포함된다. 폴링만 제거하면 전체 시간이 줄어든다는 증거는 없다.

## 다음 구조적 경계

동일 authorBatch 내 70회 graph projection을 줄이려면 변경된 frame과 계약/소스 관측을 하나의 명시적 트랜잭션 모델로 관리해야 한다. 독립 환경에 걸쳐 전체 Registry를 무조건 캐시하거나 변경된 원본의 검사를 생략하지 않는다. 별도로 빌드 도구 및 C# 프로세스 재사용을 검토하려면 정확한 SDK·컴파일러·타깃 입력 및 진단 의미를 보존하는 프로토콜이 필요하다. 전체 Check 및 도달 Build의 범위 차이와 원본/툴 변경 검사는 그대로 남는다.

실제 Chromium 정상 3회와 충돌 시나리오 1회, 상주 스트림 프로토콜 회귀를 통과했다. 합성 두 프로젝트의 원본 격리, 외부 그래프 및 donor 계약 변경 감지, 체크포인트 저장 충돌/Confirm 충돌 보호, 원본 C# 보존, 하나의 최종 Save/Confirm, 묶음 Undo/Redo, cold 재개방, 실제 새 기능의 세 실행 분기를 확인했다. Windows 실기는 검증하지 않았다.

## 트랜잭션 읽기 모델 (853c623 후속)

동일 복합 Save의 70회 `blueprintDescribeOwned` 호출을 임시 해시 계측으로 비교했다. 요청 자체가 달라져도 구현 선언/계약/프로젝트 문맥이 반복되며, 동일 그래프 입력도 반복된다.

첫 구조적 경계는 하나의 authorBatch 및 내부 staging 모두에 같은 일회성 토큰을 부여하는 것이다. 상주 authoring 도구는 이 토큰의 모델에서 직접 소유하고 property 참조가 없는 그래프의 구현/계약 문맥을 재사용한다. 모든 관측 declaration/manifest의 내용 해시와 등록된 논리 경로의 실제 해석을 재확인한다. 한 번의 경로 검사에서 공유 경로 구성 요소를 중복 조회하지 않지만, 다음 검사에는 새 관측표를 사용한다. 변경 또는 범위 초과는 기존 계산으로 돌아간다. property/상속 문맥은 기존 Registry 경로를 유지한다. 검증된 전체 그래프 계산은 완전히 동일한 입력만 재사용하며 변경 그래프, 수정된 본문, 다른 계약 및 다른 assembly 문맥은 다시 평가한다. 저장 checkpoint 및 최종 Confirm/Run의 검증은 변경하지 않는다.

실제 Chromium에서 별도 임시 hit 계측을 적용한 복합 Save는 70개 호출 중 66개가 토큰 모델에 도달했다. 그중 문맥 58회 재사용/8회 재구성, 전체 그래프 결과 30회 재사용/36회 재평가였다. 내용/경로 재확인 성공 58회의 합은 약 21ms였다. 창이나 UI의 결과 표시만 앞당긴 것이 아니다.

초기 최종 모델 실행은 다른 임시 계측 도구 빌드와 겹쳐 Save 10036ms, Confirm 6988ms, Run 4703ms였으므로 별도 표시한다. 이 결과 포함 시 Save 네 번의 중앙값은 5132ms다. 동일 기준의 신규 계측 실행 5968ms와 이전 세 번의 중앙값을 모두 구별한다. 전체 저장 및 검증 지연이 제거된 것은 아니다.

후속 단계는 각 실제 셀 변경과 관련 의존 관계를 하나의 호스트 트랜잭션에서 유지하여 70회의 분리 요청 자체를 줄이는 것이다. 현재 모델은 동일 자료의 재검증 결과를 재사용하지만 분리 호출 수를 줄이지 않는다. 함수/분기 변경 시 재구성 범위를 정확하게 제한할 수 있는 의존 그래프가 아직 필요하다.

경로 대소문자도 실제 철자별로 증명하도록 최종 정리한 뒤 stream 회귀 및 추가 정상 UI 한 번을 다시 통과했다(Save 5900ms, authorBatch 2832ms, 그래프 조회 859ms, Confirm 5971ms, Run 4339ms). 정상/계측 네 번의 중앙값은 Save 5132ms, 그래프 조회 674ms이다. 빌드 경합 실행까지 포함한 전체 다섯 번의 Save 중앙값은 5388ms로 기준과 같다. 따라서 입증된 개선은 중복 모델 계산 및 해당 호스트 구간이며 전체 체감 저장은 여전히 편차가 있다.

회귀: 동일 타임스탬프의 외부 계약 변경, 원본 파일을 변경하지 않은 locator symlink 교체, 그래프 변경과 복귀, 독립 프로젝트 scope, 기존 스트림 및 CLI 의미, 실제 Chromium의 정상/충돌/Undo/Redo/cold/실행, property 참조 저장 및 컴파일 오류·손상된 artifact 회복을 각각 통과했다. 실제 Windows 검증은 수행하지 않았다.

## 같은 셀의 이름·의도 원자 변경 (0fe054c 후속)

기존 authorBatch 내부에서 이름과 의도를 별도 graph 변경으로 수행하고 각각 현재 graph를 다시 읽었다. 직접 소유의 동일 셀에서 두 연속 변경의 입력이 정확한 경우, 이를 내부 `presentationBatch` 하나로 처리한다. 기존 개별 이름/의도 한계, 소유권 및 basis, 전체 graph 검증, 읽은 모든 원본과 revision/hash CAS를 사용한다. 슬롯 문맥과 다른 순서/노드/필드에는 기존 경로를 그대로 적용한다. 외부 API에서 임의의 내부 batch를 실행하는 경로를 추가하지 않았으며, 이 변경은 별도 checkpoint를 만들지 않는다.

| 실제 Chromium full-clean (ms) | 0fe054c 비교 중앙값 | 변경 후 3회 |
|---|---:|---|
| graph 조회 횟수 | 70 | 64, 64, 64 |
| graph 조회 호스트 합계 | 674 | 570, 488, 484 |
| authorBatch 핵심 호스트 | 2585 | 2593, 2345, 2289 |
| Save 완료 | 5132 | 4881, 3848, 3875 |
| Confirm 완료 | 5971–6455 | 6440, 5926, 6479 |
| Run 실제 출력 | 4339–4884 | 4413, 4640, 4362 |

정상 3회 및 충돌 포함 1회에서 기존 한 번 Save·Confirm, 그룹 Undo/Redo, 정상 재시작, 외부 계약/체크포인트 충돌 거절, 다른 합성 프로젝트 원본 보존과 실행을 확인했다. 추가 UI 회귀는 실제 Save 요청의 의도 하나를 허용 한계 밖으로 변경해 전체 거절 및 체크포인트/원본/호출 입력 보존을 확인한 후 정상 재시도한다. 이 단계는 6회의 조회를 실제 제거했으나 전체 authorBatch를 하나의 graph 요청으로 통합한 것은 아니다. 다음 경계는 이름/의도와 C# source를 동일 candidate의 검증된 definition hash에 연결하는 다중 소스 계획 또는 분기 변경 전체의 검증이다. 실제 Windows 실행은 미검증이다.

후보 검증 후 동일 환경에서 이전 0fe054c를 다시 실행했다. Save 4862ms, authorBatch 2384ms, graph 70회/600ms, Confirm 5972ms, Run 4251ms였다. 후보의 Save 중앙값 3875ms는 이 비교보다 약 20% 짧으며, 전체 Confirm/Run 개선은 입증되지 않았다. 기존 독립 컴파일 시험에서 동일 timestamp 소스 변경, 잘못된 C# 거절 및 손상 artifact 복구도 통과했다.
