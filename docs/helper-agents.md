# Local Agents and global Helper conversations

The sidebar counts registered Agent configurations. Installed provider declarations are available under the separate provider settings list and in **Agent 추가**. Saving or registering configuration does not authenticate an account, run a model, or grant project access. The supported reply transports remain Codex and OpenAI Responses; **설정 → 외부 ChatGPT 연결** manages the separate MCP engine connection. Agent registration contains no external connector or project scope grant.

From **Helper 추가**, create a Helper with an immutable personality and speciality, or import the existing Main Helper template. A new Helper requires a registered Agent and can exist without a project. Retained records without an Agent stay on disk and appear only in the import picker. Display profiles, recruitment templates, project membership, memory and Agent assignment remain separate. Choose a registered configuration in the v508 Helper form's Agent picker; project-only Helpers can be reassigned only in their own open project.

Global Helpers have **전역 대화** independently of the selected project. Review the exact message, Helper profile, completed conversation history, model and provider permissions before each request. Common memory is excluded by default and selected for each turn. Project memory, legacy private memory, project references, filesystem/process capabilities and development tools are absent from this request. Codex still requires its existing preflight and six separate request approvals. Unsupported methods or unverified models cannot be enabled by approving the content.

Only actual provider events become replies. Draft saving, configuration registration and conversation history saving have separate states. A failed or cancelled request keeps the input, carries its original request identity and does not display a previous answer as the new result. Closing and reopening a conversation reads its local journal without replaying a provider request. History pages affect display only; the complete approved context is shown again before each transmission.

`Confectory.EditorHome.Model::HelperAgents` owns the registry, Helper store reference, approval preview, request handles, cancellation and history CAS. `ProjectAI.Configuration` / `Permission` supply existing configuration and consent contracts; `Agent` dispatches the existing provider adapters. Global consent pins an empty project ID plus `contentScope.kind=helper-global`, the Helper identity and conversation identity. A global grant cannot authorize project tools. Project chat still uses the existing ProjectContext, Helper selection, AI owner and Review/Confirm flow; the selected Helper's registered Agent supplies its connection. A project roster grants internal Helper access; changing the active conversation does not delegate the durable Main Helper role or modify external MCP grants. Disconnecting an Agent retains its configuration and Helpers and retires prepared approvals. Starting a request rechecks the current owner/configuration/offline state.

The registry is `helper-agents.json`; conversations use hashed Helper identities under `helper-conversations`. Neither file stores approved rights or credential values. Configuration contains the existing external credential references. CAS conflicts preserve the original files. Malformed registry data leaves Home available with a fixed diagnostic. A failed history save retains the current response and reports the persistence failure separately.

## Character display and request context

**설정 → 화면 → 도우미 캐릭터 표현 표시** controls the local EditorHome profile, pinned card and 3D display. The Helper request context comes from the recruitment template and scoped memory. The display description, portrait and workspace presentation preference are outside that context. [Display preference storage](../packs/editor-home-model/HomePreferences.csbody) · [Helper context projection](../packs/helper/Command.csbody)

Project and global Helper preparation both include the template's `personality` and `speciality` as separate fields. Both are required free text at recruitment. For example, the built-in Main Helper puts its work role in `personality`. Memory and completed global history may also contain work facts or relationship language. Memory scopes govern which records are eligible, and the context defines no separate relationship field or marker for optional character-only text. [Recruitment and global preparation](../packs/editor-home-model/HelperAgents.csbody) · [Project preparation](../packs/editor-home-model/Command.csbody) · [Scoped memory](../packs/helper/SCOPED_MEMORY.md)

The current approvals cover the intended content, owner scope and provider use. Codex and Responses carry the prepared context into their request content and resolve tool access separately. There is no independent per-user policy to omit optional character context from normal Helper turns. A future omission would need structured, explicitly optional fields and a separate local policy checked at preparation and dispatch. Omitting input would limit what the request supplies. It could not guarantee that a model makes no inference from the message or permitted context. [Chat-use authorization](validation/chat-use.md) · [Codex adapter](../packs/agent-codex/Provider.csbody) · [Responses adapter](../packs/agent-responses/Provider.csbody)

Public project chat is a separate human collaboration path. Its admitted sender, explicit message text and eligible sealed attachment are handled by the public chat owner without assembling Helper context. [Editor chat adapter](../examples/editor-home/LocalChatExchange.csbody) · [Public chat contract](../packs/project-chat/README.md)

The Linux Chromium regression compares the actual Responses project review and the global preparation result with the display setting on and off. It checks explicit memory selection, another project, unchanged approval requirements and no connection to the loopback provider fixture. It stops at preparation, before any provider dispatch. [Offline regression](../tests/web/v821_helper_request_context_ui.py)

Current bounds are two supported provider configurations, 256 Helper assignments, eight retained global request owners per engine, 24 records per conversation, an 8,192-character message and a 49,152-character reviewed context/message budget. The UI reads two history records per page. Reaching a context or retention limit refuses the next request; it does not silently drop history or replay an old request.

The v508 startup layout waits for the actual initial model snapshot, offers Agent connection or **나중에**, and respects reduced motion. Creation uses the project/packs tabs, native parent-folder ticket, retained input and the existing empty ProjectPack creator. The selected roster order determines the Main Helper. With a registered Agent and no selection, creation can recruit an Agent-owned Main Helper. Arbitrary pack combinations, generated images, account login and unsupported providers are not simulated. A creation proposal owns a separate draft from the ordinary creation form.

Validation uses the actual public model, HTTP/stdio adapters and Chromium UI with owned loopback HTTP and Codex protocol fixtures. It does not use a paid inference service, a user account, permanent permission creation or a user project. Linux checks and Windows compilation do not establish behavior on a user's Windows PC.
