# 열린 프로젝트의 권위 있는 메타데이터 전달 및 관계 변경분

기준: `316cbd33025dbb43cfc7c63d8127bb4535d436b2`. 실제 Linux EditorHome, Chromium 151, .NET SDK 10.0.401. Windows 실기 미검증.

## 두 구조적 변경

1. 대규모 데스크톱 PackWorkspace의 관계도 projection은 이전의 bounded 순수 노드/edge 결과를 소유자별로 보관한다. 모든 현재 소유 단위는 기존과 같이 읽고 ID/종류/revision/정확한 draft text SHA-256/dirty를 확인한다. 동일한 단위는 authoring RPC에 원문을 다시 보내지 않고 동일 projection을 재사용한다. 변경 단위만 파싱, 제거된 단위는 제외, 전체 순서와 외부 참조/grouped edge는 기존 규칙대로 재구성한다. 전체 마지막 재검증은 생략하지 않는다. 캐시는 workspace 범위의 최대 2048행·2,097,152문자이며 종료 시 기존 workspace 상태와 함께 폐기된다. **캐시는 물리적 파일의 최신성이나 소유권 권한 증명이 아니다.** 외부 물리 스키마를 다시 읽는 기존 정확한 검사와 저장 CAS, 검토, 삭제/복구는 유지한다.
2. EditorHome의 공개 `inventory` 및 `relationsMap` 상태는 권위 있는 버전이 일치하면 전송에서 반복된 전체 필드를 생략한다. 인벤토리의 정확한 공개 투영 해시는 권위 있는 catalog read 시 한 번 계산하고, 관계도는 전체 map을 덮는 기존 버전을 사용한다. 실제 host Refresh/상태 생성/revision/스코프 검사는 수행한다. 새 버전, 누락/틀린 참조, 미지원 소비자는 전체 필드 응답을 받는다. 클라이언트는 각 요청 당시 캡처된 동일 scope의 immutable 값만 참조하고, 오래된 응답이나 토큰 불일치를 거절한다. 기존 요청 result/replay/cancellation 계약은 변경하지 않았다. 이 기능은 명시적으로 opt-in한 bundle에만 사용한다.

## 병목 분리

400개·8창 기존 cold의 실제 host `localInventory` 소비 약 312ms 중 grouped `relationsMap` authoring 약 80ms, 세 `openEditorView` consumer 각각 44/43/54ms 표본. 일반 저장은 훨씬 더 큰 반복 검증이다. 400개 실제 직접 문자열 저장 표본에서 준비 `blueprint` consumer 약 331ms와 `directPropertyConfirm` 약 342ms가 측정되었다. 그 안에서 property/type/body group 검사, observation, overlay, review summary 등을 여러 차례 호출했다. 관계도만 줄여도 일반 저장 전체를 수십 ms로 만들 수 없다.

실제 400개 연속 저장에서 관계도 source row는 최초 403개, 이후 일곱 번의 저장 각각 **1개 재파싱 + 402개 재사용**. 관계도 consumer 시간 표본(8회): 기준 53.2/47.0/76.9/31.9/32.8/78.6/66.7/29.8ms, 변경분 후보 26.6/23.8/14.1/12.3/20.1/14.9/15.8/12.5ms. authoring RPC는 기준 약 17~68ms에서 변경분 약 0.5~4ms로 감소. 외부 물리 schema 추가는 별도 기존 host 검증으로 새 필드를 읽으며, 그 시점에 권위 있는 draft row가 바뀌지 않았다면 기존 동일 draft projection은 재사용한다. 실제 저장으로 draft가 변경되는 경로에서 1행 재파싱을 별도 검사했다.

첫 번째 대량 필드 해시 재계산 후보는 응답량은 줄였으나 warm 명령 준비가 세 표본에서 느려져 그대로 채택하지 않았다. 최종은 권위 있는 catalog 생성 시 한 번의 버전 계산을 사용한다.

실제 Chrome Resource Timing의 동일 origin `/api/request` encoded body size 합계(Home 카드 click부터 검색 확인). 응답량 감소는 두 교차에서 일관적(약 warm 32%, cold 49~53%)이나 총 UI 시간의 모든 표본이 개선되지는 않는다. 다른 기준선 표본과 기계 변동이 있으므로 일반 UI 시간의 보장된 감소율로 해석하지 않는다.

400개 같은 속성 창 연속 5회 실제 문자열 저장(click→원본 persisted + 성공 UI, 각 작업 완료 후 일반 명령 준비 대기) 중앙값 기준 1174.9ms → 최종 1171.1ms. **일반 저장 시간의 의미 있는 개선은 미검증이다.** 최초 시험에서 실제 명령 준비 전에 반복 입력하여 두 실패가 있었으나, 준비 확인을 추가한 동일 창 테스트는 기준·최종 모두 통과했다. 별도 재열기 반복은 다른 비교이며 동일 창 결과와 혼합하지 않았다.

## 최종 보호 및 검증 결과

- 실제 40/400개 8창의 저장 필터·외부 schema 갱신·두 미저장 입력, 외부 변경 후 필터 자체의 schema 재검증, 명시적 지도 갱신 모두 통과. 400개 실제 동일 draft 지도 재조회는 **409개 재사용, 0개 authoring parse**; 재조회 UI 시간 단일 표본 280→267ms(일관 latency 개선 주장은 안 함).
- 실제 400개 연속 저장 5회와 일반 문자열/정수 저장·재시작·외부 소유자/읽기 불가 보호. 바뀐 draft row만 재파싱 검사 통과. strace 컴파일러 실행 0, 프로젝트 DLL open 0. 40개 동일 창 연속 저장 및 보호도 통과.
- Worker Review에서는 오래된 검토 거절, 두 원본과 입력 유지, 명시적 검토 후 정확한 두 번째 Worker 소스만 채택.
- 400개 객체 역참조 거절, 취소, 삭제 확정, 재시작 및 복구, 동일 ID의 다른 프로젝트 격리. strace 컴파일러/DLL open 각각 0.
- 참조 값 선택/저장 전후 컴파일/DLL open 각각 0, 명시 Run에서 컴파일 7, 프로젝트 DLL open 84, 변경된 연결값 실제 실행 및 종료 코드 0.
- `primary-external-during`, `primary-close-persist`, `stale`, 동일 namespace의 두 프로젝트 검색 및 외부 이름 변경, 캐럿/스크롤 유지 통과.
- 실제 host raw update: 전체 응답(구클라이언트), 틀린 해시 전체 응답, 정확한 공개 인벤토리 참조, 잘못된 활성화 scope 거절. Node client lifecycle의 immutable field, 요청 시점의 참조, 오래된 completion 순서, 틀린 reference 거절/remount 격리 확인. 기존 coalescing/replay/stale revision 테스트도 통과.

실험 초기에 명령/지도 준비 완료 전에 다음 입력·재조회를 시도하여 세 번 실패했고, 외부 물리 schema 갱신이 반드시 동일 draft row의 변경을 뜻한다고 잘못 요구한 한 번이 실패했다. 이 네 번은 통과로 집계하지 않았다. 실제 명령 준비를 기다리는 연속 저장 및 명시적 지도 재조회, 변경된 draft의 정확한 한 행 파싱 검증은 수정 후 통과했다.

다음 큰 병목은 저장 준비 및 최종 검증에서 동일한 큰 owned units 및 메타데이터를 수십 번 authoring 요청하는 경로다. 기존 모든 검사를 유지한 단일 scope의 exact content references 또는 read-only 검증 batch를 별도로 설계·계측할 필요가 있다. 일반 편집 수십 ms 목표는 미완료다.

공통 WebUI 비참여 앱 ButtonGame의 실제 Chromium 증가·재연결·초기화 및 기존 transport 보호 검증도 통과했다. 최초 추가 smoke 확인은 기존 에디터 전용 `goto_editor()` 대기를 ButtonGame에도 적용하여 실패했으며, ButtonGame의 실제 진입점으로 테스트를 수정한 뒤 성공했다. 최종 검증 실행에서도 격리 실행기 자손 잔류는 0이었다.
