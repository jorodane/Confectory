# V821 — staged owner context reuse

기준: b2ebf8c2b33abd8085286c8ca1a6d81ae56b8c13. Linux 실제 호스트와 Chromium, 합성 프로젝트 40/400개.

## 변경

- readOwnerEdits 준비 및 저장 확정 후 스키마 갱신에서 기존 물리 검증된 정확한 스키마 투영을 재사용한다.
- 서버가 준비한 깨끗한 단일 루트 문자열/정수/참조 편집만 compact context 재사용 대상이다. 일회성 서버 내부 증명을 원본 draft, owner, thread, 정확한 context 및 실제 staging handle에 묶고 finally에서 제거한다.
- admission 및 final 단계에서 새 Capture, checkpoint, 전체 unit 집합, 정확한 guard 및 소유권 경로의 실제 내용/해시를 확인한다. 불일치, 누락, 링크, 범위 초과, 구 프로토콜은 원래 전체 context 조회로 돌아간다. 선택적 증명 때문에 기존 2MB 계획 한도를 초과하면 증명 없이 재시도한다.
- 실제 저장의 후보 의미 검증, 물리 최종 쓰기, 충돌, 권한, 변경 감지 및 성공 확인은 그대로 유지한다. 별도의 두 번째 의미 검증 생략 실험은 mixedOwnerCopyEdits 성능 악화로 폐기했다.

## 실제 저장 호출

400개 기본 및 독립 scalar 18회 추적 중앙값(ms), 기준→최종: 준비 99.7→65.1, apply 318.4→270.7, confirm 171.7→156.2. 준비/apply inspectEffective 중앙값 각각 2→1; admission 재사용 18회, final 6회. 역순 독립 scalar 9회 apply 268.1→250.9, confirm 182.8→184.4. 역순 참조 기본 준비 92.5→48.4, apply 380.7→364.2; 독립 준비 131.4→94.0, apply 447.5→426.2, confirm 180→214.2. 따라서 최종 물리 확인 시간 개선을 주장하지 않는다.
