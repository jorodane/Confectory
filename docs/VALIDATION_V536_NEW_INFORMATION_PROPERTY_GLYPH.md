# v536 새 정보 속성의 생성·값·아이콘 결합 저장

기준은 게시 `1b1021b`와 저장소 `196c605`의 v536 ZIP이다. 원본의 새 속성도 같은
`renderFields` 행과 `editIconValue(..., true)`를 사용한다. 따라서 저장 전의 새
속성에서 기호/이모지를 선택하거나 `아이콘 없음`으로 해제하는 것은 새 디자인이
아닌 기존 I6 조작이다. 이번 최소 단위는 **소유 정보의 새 직접 루트 속성 →
이름/타입/기본값·glyph 편집 → 기존 Save → 재시작·Review/Confirm**이다.

## 구현과 보존

원래 새 속성 행의 버튼과 기존 단일 팝오버를 연결했다. glyph는 생성 초안 셀의
선택적 `icon`에 보관하며 값 입력과 분리한다. 이름·기본값·타입 편집은 최신 셀을
갱신하므로 이전 closure의 값으로 glyph를 덮어쓰지 않는다. 기존 속성 Undo·닫기·
Escape·초점 복귀·명시 해제와 원본 CSS/레이아웃을 그대로 사용한다.

이미 생성기에 존재하는 `p_<uuid>` nativeKey를 재사용한다. 새 핀 ID나 독립 계약
복제는 추가하지 않는다. 기본/typed 정보 정의의 생성 후보가 glyph를 검증하고,
선언·표시 이름·정확한 기본값·`editorFieldIcon_<nativeKey>`를 같은 후보/CAS로 저장한다.
잘못된 마지막 glyph나 범위 밖 숫자는 필드만/metadata만 남기지 않고 전체 미적용이다.
빈 glyph의 명시 해제는 새 필드를 지우지 않고 해당 아이콘만 없애며, 다른 원문·
값·설명·요소/부모 아이콘·참조·부모/외부 파일·실행 권한은 보존한다.

응답 유실은 기존 저장 receipt 조회를 먼저 사용한다. 성공 응답을 기다리는 동안
glyph만 바뀌었다면, 생성된 nativeKey·이름·계약·값·수락 glyph와 source hash를
확인한 뒤 그 필드의 후속 `schema-icon` 입력으로 옮긴다. 새 입력을 버리거나 필드를
다시 생성하지 않는다. 대상 입력 키가 이미 있으면 덮어쓰지 않는다. 다른 생성
내용의 늦은 변경을 이 경로가 임의로 재해석하거나 자동 재기준화하지 않는다.

실제 회귀에서 생성 계약의 JSON 키 순서와 조회 계약의 순서 차이로 이 receipt
연결이 실패하던 결함을 재현했다. 같은 세 의미 필드(kind/cardinality/type)를 같은
순서로 비교하도록 수정했다. 타입 값·소유권·원래 source·checkpoint·최종 CAS
조건은 완화하지 않았다. 새 glyph는 재시작 후에도 별도 입력으로 보존되며 새
명시 저장만 적용한다. 다른 창의 미적용 입력은 유지하고 최종 Review는 기존 보호를 따른다.

## 새·중첩 흐름의 원래 범위 구별

| 원본 조작 | 판정 |
|---|---|
| 새 직접 정보 속성의 저장 전 glyph/명시 해제 | 이번 생성 후보·기본/독립 창 수용 범위 |
| 연결된 정보의 하위 값 표시 | 원본 `renderFields`는 linked 하위 값에 inheritedMode를 전달한다. 참조된 정의를 현재 값 화면에서 임의 편집하는 요구로 확대하지 않음 |

| 부모/외부 원본 변경·공개 override 입출력 변경 | 기존 소유권·원계약 보호를 유지. 독립 계약 복제는 필수 제외 |
