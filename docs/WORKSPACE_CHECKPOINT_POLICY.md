# Measured Workspace checkpoint policy

The user's Windows observation was investigated through code and an actual ordinary EditorHome/ordinary ButtonGame ProjectPack in Linux Chromium. Windows runtime write frequency is not inferred from that measurement. HTTP invoke requests, actual presentation-file replacement events (inotify MOVED_TO for the real JSON file), and status-text mutations are counted separately. The test uses no alternate ProjectPack, provider or build exception.

Before: idle/model polling and repeated focus produced zero requests/writes. Repeated right-click menus produced 5 requests/5 real replacements; repeated origin reset 5/5; a 300ms-spaced wheel burst 8/8; nine characters at 300ms intervals 9/9. Pan and window movement each produced one replacement at gesture end. Re-sending an identical snapshot produced one real replacement. Every automatic save cycled pending/saving/saved status. [Before measurements](evidence/layout-checkpoints/before.json). Source evidence: pan persists at gesture end, wheel and note input call host.persist, schedule previously incremented its version unconditionally with a 250ms debounce, and Model.Command wrote every validated savePresentation unconditionally.

Durable window positions/sizes/folds, notes/groups/Workspace membership and final camera state now stay dirty in memory and checkpoint on a 15-second periodic tick when changed. Idle ticks do nothing. Right-click menus, hover, visual focus and drag-selection highlights are transient; selectedNodeKeys are no longer part of the new persisted snapshot or dirty comparison. Actual selected semantic object/editor bindings and browser navigation remain the meaningful restoration contract. Existing old presentation records remain readable. Pointer movement is not itself a save request.

Unsubmitted source/schema/editor/Helper/chat/direction/Yogi-description input and note text retain a separate fast checkpoint: 750ms of quiet or a maximum two-second input window. These meaningful input saves may carry the current placement with them; no input is dropped to wait for the layout period. The layout tick defers while input checkpointing is pending. Yogi package contents persist through their separate domain Save/CAS contract; this policy does not move them into UI data. Ordinary engine commands flush pending input, not every dirty layout. Explicit project hiding/complete close and the acknowledged close hook flush the entire latest state. Saves serialize and retain dirty contents on failure.

The client compares acknowledged snapshots; the domain also uses JsonNode.DeepEquals to skip WriteAtomic for identical data. Automatic success stays quiet; a stable changed indicator is shown once rather than repeated pending/saving/saved messages. Actual failure/restore errors remain visible. A failed file write is not acknowledged as saved. No source Apply, Save/Review/Confirm, permission, provider call or command replay is introduced by checkpointing.

Windows WebView normal close confirms user intent, requests the optional page's acknowledged presentation/input flush, then invokes the existing native complete-close contract. A false/failed/timed-out flush leaves the workspace open with an error. The hook does not expose host objects or broaden native actions; it uses a source-checked, request-key-matched acknowledgement. Native Windows execution/user PC are held; managed build verification is separate. Browser page/tab close cannot reliably await asynchronous work and is not claimed to guarantee a final flush. The same limit applies to a crash, kill, machine failure, disconnection or unwritable storage. A 15-second layout interval describes the nominal recent-placement loss bound only while the host can save; busy operations or actual save failures may extend it. Input's nominal two-second/750ms window likewise requires a running writable host and does not guarantee forced-shutdown durability.
