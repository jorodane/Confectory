# Codex startup readiness and text-frame diagnosis

This change follows `7ce8d3eb8f69a16aa02676cd34ac503376014c28` and supersedes its send-only renewal behavior. The engine now begins a bounded background readiness check for an existing active, registered local Codex Agent when the editor session starts. No Helper, settings dialog or Send action is needed to start it. The sidebar and settings dialog project the same backend readiness state.

## Startup and settings

Startup inspects only the registered executable, configuration and pinned account identity using the existing four inspection permissions. It does not discover another installation, install software, initiate login/OAuth, register a new Agent, switch an account or authorize an inference turn. Explicitly disconnected Agents and registrations without a verified identity do not start a CLI. A missing executable, unavailable authentication, different identity, failed inspection or cancellation remains blocked. The pinned identity is never rewritten by readiness renewal.

Duplicate startup/Send checks join the owned verification instance. Verification retains its existing timeout, restricted environment/tool policy and final dispatch fences. Explicit retry and cancellation operate on the registered Agent and the owned check ID. Closing the engine retires a pending owned process; disconnecting an Agent also cancels its pending inspection. Temporary readiness is still session evidence, not a persisted authentication claim.

The browser and native poll lifecycles now publish checking/terminal Agent states even when no conversation or setup job is active. An isolated browser reproduction caught the missing publish trigger: the CLI had finished inspection but Home still showed checking. Settings reopening now hydrates an inert ready view from matching verification evidence and the server-owned registration. That hydration neither saves settings nor re-registers the Agent. A deliberate account change still enters the explicit login flow. Active manual setup failures are not hidden by an unrelated old ready view.

The v508 layout, CSS, dialog/button structure and original ZIP are preserved. Existing checking, ready, failure, cancel and retry controls are reused. ## Text frames and the reported failure

The user's `洹 [provider-error · response-events · JsonException · item/agentMessage/delta]` does not establish the Windows root cause. The adapter appends `params.delta` as text; it does not parse that text as JSON. The previous diagnostic retained the last notification name while parsing the next JSONL frame, so a malformed following frame could be reported as a delta-handler failure.

Pipe stdin/stdout now explicitly use UTF-8, with strict decoding of stdout; stderr uses UTF-8 and remains drained without exposing its contents. A fresh frame resets the event label. Safe diagnostic phases distinguish `frame-read`, `frame-parse`, `event-handle` and `rpc-response`; invalid UTF-8 can report `DecoderFallbackException`. These fields pass through fixed allowlists. No raw frame, prompt, exception message, path, account data or stderr is added to diagnostics. Existing upstream failures and safety refusals remain failures.

The production adapter passed byte-at-a-time Korean, emoji, quote, newline and non-JSON-looking plain-text deltas, including completed-text reconciliation. A valid delta followed by invalid JSON reports `JsonException / frame-parse` without the stale delta event label. Invalid UTF-8 reports a decode failure; buffered reads may detect it before the turn-start acknowledgement, so its stage can be turn-start or response-events. Tests explicitly reverify their isolated fixture after such a pre-dispatch failure, rather than weakening the product guard. [Unicode rendering](codex-startup-state/unicode-reply.png) and [frame diagnosis](codex-startup-state/frame-parser-error.png) were visually reviewed.

An independent Linux probe kept UTF-8 decoding even with the console set to code page 949. Thus neither that probe nor the explicit UTF-8 hardening proves the user's Windows default encoding or resolves their actual service response failure. The [official app-server documentation](https://learn.chatgpt.com/docs/app-server) describes JSONL transport and appended text deltas. Retained generated notification schemas also declare a string delta with thread, turn and item IDs. The checked fixture shapes are not a full pinned experimental request-schema or live-account compatibility proof.

## Validation and limits

Exact source hashes and results are in [the JSON record](codex-startup-state.json). Distinct checks passed:

- Release solution build: zero warnings/errors; dynamic production model/adapter bodies compiled through integration and Windows packaging.
- Backend Agent diagnostics and existing cancellation/bounds/locality checks; owned Codex stdio/tool/scope/revocation/concurrency regressions; startup deduplication, explicit cancel/retry, zero-Helper startup and closing a pending inspection process.
- Seventeen owned browser/CLI cases across three runs: authenticated startup/settings/send, Unicode, malformed frames, startup cancellation/retry, logged-out and install-with-empty-account-home, account mismatch, expired authentication, disconnected/unverified/missing-runtime registrations, inspection failure, RPC/exit/upstream errors. Saved registration bytes and login counts stay unchanged during startup renewal; no blocked renewal dispatches a turn.
- Current global Helper UI, v508 chat geometry/IME/draft/history/error/cancel contract, plugin isolation and browser login contract. The project/pinned cold-restart harness now waits for the assigned Helper to be reflected in the UI and targets the opened chat, excluding its hover preview; its chat geometry, unsent input, pin, worker approval, source-preservation and restart assertions remain intact. [Restored project panel](codex-startup-state/project-pinned-restored.png).
- Retained notification shapes: 17 fixture cases, 15 deltas, 13 completed items, 13 completed turns, one error event and 17 turn-start responses.
- Windows x64 cross-package and composition/runtime-startup probe: 2,225 files, 50 resources, unrelated working directory, owned profile/override preservation, tamper and missing dependency rejection. All 14 changed runtime source files match the package byte for byte.

Exploratory legacy v318 AI and v480 profile harnesses failed while seeking the removed `[data-recruit=global]` menu; those menus were not restored and those failures are not counted as passes. The project/pinned regression initially selected the hover preview before its external fixture assignment had reached the page; the added readiness assertion and precise chat locator fixed that harness and its complete scenario passed. A Unicode browser assertion initially expected a literal newline in normalized rendered text; it now separately verifies the exact stored newline and both rendered text fragments. No whole-suite pass is claimed.

No user auth file/token was read, no real OAuth or paid inference was performed, and no original settings, account data, project, Android file or main branch was changed. All account/runtime/provider tests used owned fixtures. Native Windows apphost/WebView2/double-click and the user's real account response remain unverified. Run `Builds/Windows-x64/Confectory.exe` with its whole folder present; Microsoft .NET Desktop Runtime 10 x64 and WebView2 Runtime are prerequisites, not automatically installed by this work.

Read-only build inspection found output replacement with a retained previous package, not deletion of the authentication/profile directories. Packaged storage resolves HOME_STORAGE, then ENTRY_STORAGE, then an existing checkout profile, then LocalAppData. Checkout launch uses HOME_STORAGE or its checkout profile; ENTRY_STORAGE alone or moving the package can therefore select another profile. This is a verified routing difference, not a diagnosis of the user's rebuilds, and was left unchanged to avoid an unsolicited data migration.
