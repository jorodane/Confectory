# Registered Codex readiness after restart

This validation follows `1265455e8eb29cdad2261574b17b96c990ac63da`. The reproduced startup problem is loss of a process-only readiness lease, not demonstrated loss of the user's saved authentication. The user's separate `[provider-error · response-events]` failure remains unresolved on their Windows PC.

## Renewal behavior and boundaries

An explicit Send by an existing Helper now renews missing or expired readiness for its already registered local Codex configuration. Opening the engine or Helper alone does not run a CLI. Renewal reads the registered executable, managed home, model and pinned account from the backend registry; it accepts no caller-supplied paths, configuration or identity. It does not run discovery, installation, login, account import, Agent registration or an inference turn.

The original four inspection rights cover the selected process, official account metadata, effective configuration/model/tool policy and temporary storage/thread. Unknown inspection requirements block renewal. The normal per-message content/usage authorization and existing project/global scope checks remain separate. The shared project Helper preparation path uses the same readiness method and retains its explicit project preview and Review/Confirm boundaries.

The preflight uses the existing restricted CLI transport. It may initialize the CLI, perform official `account/read(refreshToken:false)`, inspect configuration/models/controls and create a temporary environmentless thread. No chat content is sent until readiness and request authorization succeed. This code does not directly read auth/token files or copy credentials. All validation here uses isolated fixture accounts/runtimes, not the user's credentials.

Renewal requires an existing non-offline local CLI registration with a pinned identity. Matching live evidence is reused. Only missing proof or the normal expired/installation-stale lease state may start renewal; cancelled, revoked, failed, unregistered or unsupported selections do not silently obtain another grant. Missing authentication and differing account metadata block. The stored fingerprint is neither normalized nor automatically replaced, and a metadata difference is not asserted to prove a person switched accounts.

Inspection runs asynchronously with bounded UI polling, rather than waiting under the editor owner lock. An ephemeral attempt token pins the registered configuration/account and verification instance. Concurrent begins reuse the pending attempt. Polling with a foreign token or changed binding fails. Shutdown retires only an owned, still-checking verification instance and does not close a replacement receipt. No persisted settings schema or registration rewrite is needed. The global prepare/start policy independently checks the registered account pin, in addition to the unchanged final provider verification fence.

The original v508 chat DOM, CSS, input/button layout and settings dialog are unchanged. Enter/Shift+Enter, draft-generation protection, explicit retry, history restoration and error/cancel behavior from the previous change remain in place. No automatic actual model dispatch is replayed on a failed/uncertain acknowledgement.

## Safe response-event diagnosis

`response-events` identifies the stage reading/handling notifications after a turn starts. Its generic code alone cannot identify a network, model-entitlement or parser failure. Existing terminal diagnostics now retain and display allowlisted exception types, protocol error variants and event names alongside stage and integer status codes. For example, malformed JSON yields `JsonException`; a foreign event is rejected with `UnauthorizedAccessException`; a known upstream variant can expose `badRequest` and `error`. Unknown values are not copied verbatim.

Raw remote messages, additional details, prompts, account metadata, paths, token values and stderr remain excluded. Errors and failed completions remain failures. The exact user-PC cause and live-model success are not inferred from passing fixtures. A new bracketed failure suffix is the next information needed from the user; no auth file, token or raw stderr is required.

The [official app-server documentation](https://learn.chatgpt.com/docs/app-server) describes version-specific schema generation and structured turn/error events. Retained generated notification schemas were used here for wire-shape checks. The fixture previously omitted required `completedAtMs` and turn `items` metadata; its JSON send path now includes them. Delta, completed-item, failed-turn, error and turn-start response captures are validated against those schemas. This is notification-shape coverage, not a passing full experimental request-schema check or live-service compatibility proof. Fetching additional pinned source/schema material was limited by GitHub source/API access restrictions; no access restriction was bypassed.
