# First-login state and recovery

Baseline: `eea0a3a6b8085ca782838754d33a24893b1c9009`. The defect addressed here is an incorrect presentation of first/unverified connection state as an already-failed login or an existing connected account. This work does **not** establish or fix the cause of the user's separate Windows policy-check failure.

A discovered CLI/home, a saved settings file or an unverified Agent registration is no longer sufficient to show retry/account-change language. First, unverified and cancelled states show **로그인**. A real preparation/policy block stays visible with its existing safe diagnostics and is separated from authentication state; Login can enter the already-permitted new-space consent path or required preparation. No restriction is treated as successful.

The onboarding owner records whether an install/login was explicitly started, a returned account/model was explicitly selected, and a login completed before a connection failure. Failures identify the attempted action: setup, installation, login or connection. The UI uses that provenance for the appropriate recovery label. Missing legacy provenance is conservative and does not invent an authentication failure. A connection-form load error now offers reopening the connection screen rather than claiming a failed login.

**계정 변경** requires a registered account identity, rather than an executable/candidate or a registry row alone. Registered users still share their existing readiness state with the sidebar/settings. Automatic startup verification is retained; an automatic connection block offers **연결 확인**, and an explicit check can be retried as **연결 다시 확인**. A legacy registration without confirmed identity remains Login, and startup still refuses to authenticate/register it automatically. Offline, actual mismatch and cleanup barriers remain enforced.

A successful new login followed by failed connection verification retains that distinction on recheck. The explicit retry inspects the same newly-created home and checks account/configuration/policy/model again; it neither rescans unrelated accounts nor starts another OAuth login. No user credentials, settings or projects are copied/deleted. No persistent-use grant or permission policy is created or broadened by these presentation fields. The actual Provider, AccountLogin, PluginIsolation, registered startup/readiness, scoped grant and tool-guard implementations are byte-unchanged from the baseline. The Command change only identifies a settings-save failure as a connection failure.

No CSS, original v508 archive, modal geometry, Android source or main branch was changed. Existing controls render the corrected states/actions; no settings redesign or developer panel was added.

- The shipped presentation and renderer with its CSS rules passed 18 isolated browser states/actions: pristine, candidates-only, settings-only, missing/invalid account identity, cancellation, real preparation block and diagnostics, process-preparation failure, explicit login/install failure, login-completed connection failure, known connected/automatic-blocked/auth-required/mismatch/offline, cleanup refusal and discovered-account choice. - The actual generated engine/Chromium/owned CLI fixture passed 13 distinct scenarios: first-unverified, first-policy-block, post-login-policy-block, logged-out, cancel-login, failed-login, bad-install, restart-unverified, restart-cancel, restart-expired-auth, restart-mismatch, restart-offline and authenticated. All identities/profiles/OAuth messages/responses were synthetic temporary fixtures, not real accounts.
- The first unverified settings screen starts no CLI request. A blocked pre-auth plugin inspection starts no account-read/login/model/turn, retains its real error and opens only a separate explicit login consent when Login is chosen. Cancel/reopen returns to Login. Actual login/install failures receive their respective retry. Post-login connection recheck requires a fresh metadata event and an enabled completed-state button, remains blocked while the cause is injected, and starts no second fake login. Registered restart cases preserve registry bytes and enforce mismatch/auth/offline without a new OAuth or registration.
- Release solution build: zero warnings/errors. Windows x64 cross-package: 2,228 files.
