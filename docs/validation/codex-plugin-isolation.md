# Codex process-scoped plugin isolation

Validation snapshot based on `83eb6f18250a653e5c18d52b264287fdea65681f`, on `work/current`. Source fingerprints in the companion JSON identify the validated implementation. This record concerns the repeated `policy-check / provider-tool-policy-unsupported / enabled-plugin-entry` diagnostic with pinned CLI `0.159.0-alpha.3`.

## Confirmed behavior and scope

That diagnostic comes from Confectory's explicit guard: a plugin entry is not confirmed to have `enabled=false`. It includes both enabled entries and missing/unrecognizable enable values; it does not identify a plugin or prove a Windows API is unsupported. The reported `installation.state=prepared` describes this flow's prepared installation. The user's exact Windows plugin configuration and the outcome on that computer remain unverified.

An actual pinned Linux CLI in fresh owned profiles reproduced the limitation: the previous option disabled one known bundled entry, while other configured entries remained enabled. `plugins={}` did not clear the merged configuration. A complete top-level CLI table containing every observed key and the known default, with each `enabled=false`, disabled all observed entries. The original `config.toml` bytes stayed unchanged and no `auth.json` was created. The child process was denied network syscalls; only `initialize` and `config/read` were sent. See [official-cli.json](codex-plugin-isolation/official-cli.json). No account, OAuth or paid request succeeded or was attempted by this official CLI probe.

## Change

The ordinary `PluginIsolation` pack helper builds a private process argument from effective plugin metadata. Provider and browser/device login both inspect effective configuration. If necessary, they stop the owned process, wait for process and stderr cleanup, start one replacement with the disabling table, reinitialize and read configuration again. A remaining/new/unconfirmed entry, failed cleanup, failed restart or failed reinspection blocks progress. There is at most one replacement per owned Provider/login operation. Account login RPCs and Provider model/thread/turn requests cannot precede confirmed plugin isolation. Post-login Provider inspection applies the same restriction again.

The process environment, startup feature denials, strict configuration, search/notification/MCP restrictions, account identity checks, request consent and per-request verification remain in force. Executable identity is checked again before replacement. Scratch and cancellation ownership survive a Provider restart. No plugin is allowed through the guard, uninstalled or revoked, and no existing configuration or credential file is rewritten/copied. The minimal v508 connection UI and its initial Login action are unchanged; external relay startup is not introduced.

Keys are untrusted. The generated TOML quotes each key and escapes quote/backslash characters; only the `plugins` table and `enabled=false` values can be emitted. Empty keys, ASCII control characters, DEL and invalid Unicode are rejected. Limits are 128 observed entries, 1,024 UTF-16 units per key and 8,192 UTF-16 units **and** UTF-8 bytes for the whole argument. The native executable receives this as one `ProcessStartInfo.ArgumentList` item with shell execution disabled. A compiled production helper and independent TOML parser check dotted, quoted, backslash, Unicode and option-looking keys, malformed shapes and bounds. The .NET child roundtrip checks exact argv separation on Linux; Windows execution is separate.

When an owned stdio stream ends before the OS exit notification, Provider waits at most 250 ms to observe a natural exit code before cleanup. It does not invent an exit code or treat EOF as success. The early-exit regression exercises this ordering.

Only failure views carry the safe isolation summary: requested/rechecked/verified booleans and bounded counts for initial/effective entries, enabled keys ending in the bundled suffix, other enabled keys and unconfirmed values. Suffix classification conveys no trust or permission. An allowlist strips unknown fields. No plugin names, table argument, full config, paths, tokens, raw RPC errors or stderr are forwarded to the diagnostic view. [Safe mismatch](codex-plugin-isolation/safe-mismatch.json), [budget](codex-plugin-isolation/safe-budget.json) and [restart RPC failure](codex-plugin-isolation/safe-restart-rpc.json) records show the format.

`overrideVerified=true` requires a replacement process and a successful effective-config reinspection. An unnecessary override leaves that flag false; the counts distinguish this from an unsuccessful requested override. The [early-exit record](codex-plugin-isolation/safe-early-exit.json) and [expanded error render](codex-plugin-isolation/early-exit-diagnostics.png) show a confirmed natural exit code without forwarding a raw exception.
