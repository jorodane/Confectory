# Helper chat recovery and request diagnostics

Validation follows `f3e38877954a94613fee74e0e9a0674c7d7562ae`. The user's Windows request failure is still unconfirmed. The reproducible account classification and history rendering defects below are fixed; isolated provider replies are not evidence of live-account success.

## Confirmed defects and behavior

The persisted Agent identity outlives the process-only, ten-minute Codex verification lease. `helper-agents.js` compared that identity with a missing verification identity before checking readiness. A fresh process, expired lease or cancellation could therefore display “account changed” for an unchanged account. A failing Chromium regression reproduced this on the previous code. Readiness now fails first with its actual reason. Missing identity in an otherwise supported preview also blocks, with `codex-account-unverified`. Different verified fingerprints still block with `codex-account-mismatch`; fingerprints are neither normalized nor automatically replaced. They cover official account metadata, so a difference does not by itself prove the person switched accounts.

The existing onboarding completion already saves configuration and re-registers the verified identity once per completion. Tests now cover a real engine restart, Send before readiness renewal (zero CLI/provider dispatch), explicit renewal of the same account without another OAuth login, and a successful fixture turn afterward. A separately consented fixture login to another identity is followed through registration and a Helper turn. No new identity migration, account switching or credential copying was introduced.

`updateHelperPresentations` also rendered the project-only reply into the global message area after the global module had restored its journal. The global module's unchanged render stamp could then leave the reopened card blank. The project renderer now leaves the global message area to its owner. Reopening alone shows history. A deliberately delayed history response followed by a switch to another Helper cannot populate the other Helper's card. History storage loss was not established by the user's observation.

For the global Helper composer, Enter and the original Send button use the same guarded submit path. Shift+Enter inserts a newline. Composition state, `isComposing`, IME key code 229, repeated keys and pending requests prevent accidental or duplicate submission. Enter while a response runs does not turn into a cancellation; the existing Stop state remains the explicit cancellation action.

After accepted dispatch, the submitted text is cleared and the empty draft is saved. A captured edit generation prevents a late acknowledgement from erasing newer typing, even if the user typed exactly the same text. A rejected preparation keeps its unsent input. An accepted failed/cancelled message remains in history rather than being reinserted into the composer. When the composer is empty, the existing Send slot becomes “재시도”; clicking it or pressing Enter explicitly prepares another request with the last unsuccessful message. There is no automatic inference replay. New text returns that slot to Send. Existing draft CAS, conditional permission consent and project/global isolation remain enforced.

## Request failure diagnosis

The previous generic failure paragraph hid the retained provider error code. Errors now retain a bounded diagnostic object through Provider → Agent terminal snapshot → Helper journal → existing message paragraph. Only declared stage/type, process-start flag and integer RPC/native/exit/HTTP codes survive. Account metadata, fingerprints, paths, raw remote messages, additional details, token values and stderr text are excluded. The UI filters again before displaying the code/stage/numbers; partial output does not hide an error's diagnostic suffix.

Codex errors may contain a string enum or a structured HTTP variant. Both error notifications and failed `turn/completed` records are classified. RPC refusal, natural process exit, malformed JSON and foreign events remain failures. No failure or changed-account guard is converted to success. Provider policy checks, environment/tool restrictions and the last pre-dispatch verification fence remain intact.

If the user's new build still fails, the bracketed code/stage/numbers at the end of the failed reply are sufficient for the next investigation, for example `[provider-error · turn-start · rpcErrorCode=-32602]`. This example is an injected fixture failure, not the user's diagnosis. No token/auth file or raw stderr is needed.
