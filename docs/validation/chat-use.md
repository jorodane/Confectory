# Scoped Codex chat use

Baseline: `db197424dc58865bf431471e93a811da48c20f42`. This replaces the ordinary local Codex per-message review with an explicit continuing-use choice. Registration and successful readiness are **not** prior permission. Existing profiles get an unselected, first-send scope prompt; only its explicit action creates an app-owned receipt. The next message within that scope goes directly. Responses, proposals, Workers and their separate permissions retain their prior behavior; Responses has no verified account contract on which to build this lifecycle.

The existing modal shows Codex/OpenAI, the checked account label/model, Helper and either global conversation or exact project, the transmitted data categories and draft tool results, process/account/configuration/storage effects and usage/possible charges without a monetary cap. It states that the choice continues after restarting and can be revoked in Helper settings. No six-checkbox loop, default acceptance, credential import or new login is introduced. Global use never includes project files/tools. Project use allows only the owned namespace and draft changes: no Confirm, execution or other project access. Existing v508 geometry and the previously approved chat size remain; this is not full v508 restoration.

## Server boundary

`EditorHome.Model.ChatUse` reconstructs the scope from server-prepared state, the registered Codex configuration, current supported account evidence and actual project tool definitions. A scope binds provider/account/model, installation/configuration boundary, Helper, durable project ID plus normalized manifest/namespace or global conversation, declared data categories, permission IDs, semantic policy version and tool schemas. Message text and new contents within the disclosed memory category are not new permissions. Adding common memory, changing target/account/model/configuration or tool/category rights invalidates the corresponding scope. Unknown rights fail closed. Material policy changes must bump the semantic version rather than reuse old evidence.

The owner profile stores versioned `chat-use-grants.json` receipts with acceptance time, scope evidence, revision and revocation state, using compare-and-swap writes. Checksums detect corruption within the existing private-profile trust boundary; they are not signatures against a malicious same-user filesystem writer. No provider secret, token or new credential is created. The UI sends a scoped one-time challenge, never approval booleans or arbitrary grant contents. An old registration/readiness snapshot is never migrated into a receipt.

Each ordinary Codex start requires a valid server receipt even if a client supplies six true flags. It gets a private per-turn ticket that is not sent to the model. Provider writes and DevelopmentTools admission check the current receipt; revocation marks/cancels pending tickets before waiting for already-admitted work. Already admitted work may finish and transmitted content cannot be recalled. Future/queued actions are denied. Failed storage updates report failure; pending revocation remains denied in this process until a successful write. Durable revocation cannot be promised across process termination after a failed storage write, so the user must retry an unsuccessful revoke. The tested admission gate is process-local; no claim of cross-process linearizability is made.

Ten-minute technical evidence is separate from user permission. Expiry still requires current account/configuration/tool-policy verification, silently renewed under the existing registered-account authorization, without broadening the receipt or creating a login. Account mismatch/offline/missing runtime/unknown scope remains blocked. The MCP/Sites bridge only dispatches its enumerated engine tools and scoped development definitions; it does not forward the UI consent endpoint or mint chat-use receipts. External relay startup is unchanged and is not added to CLI chat.
