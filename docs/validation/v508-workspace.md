# v508 Workspace and Project Browser — stage 2

Baseline `596497635b794efa0c3eaa7b27348f0700aac7da` already contains the native titlebar adapter. This stage restores the Workspace shell, fixed Pack Manager tab, Project Browser chrome and project participant filtering against the immutable v508 reference. Semantic element editor interiors remain the next stage; this is not a claim of full v508 equivalence.

The original Workspace / Pack Manager tabs, context-menu hierarchy, creation grid and zoom indicator/menu use the original structure and styles. Workspace zoom uses the original 3.125–300% range and updates the actual canvas transform and private presentation. Existing note, child Workspace and document ownership/layout adapters remain in place. The actual engine regression covers Browser document / Workspace / Pack Manager transitions and process restart; it does not exercise every note/child Workspace gesture.

Pack Manager renders actual registered inventory. Its installed project view is the owning pack and its dependency closure, rather than every registered pack. Local inventory, private favorites, search, sorting and selection are separate. The original installed/local/explore/favorite/mine structure is retained. Marketplace, mine ownership, pack creation, update, uninstall and deletion have no complete mutation contracts here: these actions remain explicitly unavailable and never report a fictitious success. Enum creation and recent-created sorting likewise report their missing contracts/timestamps rather than fabricate declarations or order.

Project Browser restores the original concept/info/feature/module tabs, search/submit/sort/add controls, six density steps, folder tree/splitter, title path, and Discard / Save / Confirm controls. The adapter uses real declarations: schema declarations appear under Info, functions/implementations under Feature, modules under Module. Namespaces and explicit parents come from the engine; prototype objects, workers and demo history are not copied.

Save checkpoints the whole project's **applied shared working copy**, as its tooltip states. It does not write final source files. Discard restores only the displayed owned declarations to their last checkpoint, or their unchanged source baseline when no checkpoint row exists. It uses the existing atomic edit batch and explicit owner, revision, source-hash and checkpoint-hash proofs. Unapplied editor input is preserved and blocks these actions. New declarations without a restorable checkpoint fail closed; Discard does not delete registrations. The bounded status/action contract accepts at most 64 explicit declarations. Confirm opens the existing reviewed-token workflow; final compilation/Confirm remains a separate explicit action.

The browser endpoint derives context from the server-selected project, rejects unknown/client context fields, foreign namespaces and forged owner proofs, and is rejected in connection settings. It adds no provider tools, account grant or final Confirm privilege. A stale transport admission can be retried only because it guarantees non-execution; the original CAS proof remains unchanged. Unknown outcomes or actual draft conflicts are not automatically accepted.

Inside a project, participant lists and Agent hover contents include only Helpers placed in that project. Outside projects, the full global list remains available; Helper + retains unplaced placement candidates. Human and Agent rows are preserved. Unassignment hides a retained pinned card and disables project input without deleting its draft or conversation. Reassignment and process restart restore it under the same project identity. Existing server placement/grant guards still reject unassigned and other-project chat requests.

## Distribution and remaining scope

Use the entire `Builds/Windows-x64` folder and open `Builds/Windows-x64/Confectory.exe` on Windows. Keep the accompanying files together. The previous local distribution was preserved outside the source tree. Microsoft .NET Desktop Runtime 10 x64 and Microsoft Edge WebView2 Runtime are prerequisites; neither is installed automatically. An SDK is needed to compile user projects, not to open the packaged editor.

This Linux environment did not execute the Windows apphost/WebView2, double-click workflow, native titlebar, drag/snap, DPI or native account flow. Browser and managed-process tests do not establish those results. Previously verified connection/account/consent implementations are preserved, and no new live model success is claimed.

Next: restore semantic element editor interiors screen by screen against v508 — inheritance/overrides, properties, feature/module composition, embedded Browser and save/review behavior — by adapting existing backend contracts. Audit unsupported operations before implementation, retain owned draft/review/security boundaries, and do not replace the original layout with generic forms or copy demo data. Existing user-data compatibility must be verified per adapter; no migration is presumed necessary or authorized by this UI stage.
