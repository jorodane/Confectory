# 검증 작업공간과 패키지 보관 수명

이 변경은 Linux 검증 도구에만 적용한다. 에디터 레이아웃·기능·권한·저장 계약과 일반 사용자 프로젝트의 빌드 캐시 정책은 변경하지 않는다. 기존 `Builds`, `artifacts`의 과거 패키지, 기존 checkout·캐시·프로필·로그·스크린샷을 정리 대상으로 채택하지 않는다.

## 실행

```bash
PYTHONDONTWRITEBYTECODE=1 python3 tools/verify_desktop.py \
  /workspace/Confectory /workspace/artifacts/v536-verification-managed \
  --commit <검증할 전체 commit SHA> \
  --sdk /workspace/toolchains/dotnet-10.0.401 \
  --nuget-seed /tmp/confectory-site-nuget
```

실행 전 RAM 파일시스템, cgroup 메모리와 지속 공간을 검사한다. 초기 예산은 압축 패키지 최대 56MiB 세 개(최신·롤백·승격 후보), 증거 20MiB, 코드/메타데이터 4MiB, 안전 여유 64MiB다. 새 보관 패키지는 ZIP_LZMA를 사용하며 실제 ZIP이 56MiB를 넘으면 승격하지 않는다. 보관소가 만들어진 뒤에는 새 후보 한 개가 필요한 추가 공간을 계산한다. 동일 commit 반복도 모든 빌드와 검사를 새로 수행하지만 검증된 기존 최신본·별도 롤백본을 교체하지 않는다. 안전 여유를 줄여 실행시키지 않는다.

ZIP_LZMA는 내부 보관 형식이다. 이 Linux 도구의 `PackageStore.restore()`는 전체 파일/권한/SHA를 검증해 실행 폴더로 복원한다. 기존 DEFLATE 보관본도 읽는다. Windows 기본 압축 해제 프로그램의 LZMA 지원이나 Library 배포 형식은 검증하지 않았다. 납품 전에는 복원한 실행 폴더/선택한 전달 형식을 별도로 검증해야 한다.

반복 재사용은 source commit뿐 아니라 SDK와 NuGet seed의 전체 상대 파일명/내용 해시, Release/win-x64 입력 식별성이 모두 같을 때만 허용한다. 검증 종료 시 의존성 입력을 다시 확인하며, 중간 변경이면 승격하지 않는다. 같은 commit이라도 SDK/의존성이 다르면 별도 후보와 공간 예산이 필요하다.

## 검증 독립성과 증거

* 실행이 생성한 RAM 디렉터리 하나에 LF/CRLF checkout을 각각 `--no-hardlinks`로 생성한다. 소스 commit/tree, Git 설정과 모든 추적 파일의 EOL 상태를 기록한다.
* 두 checkout은 각각 빈 엔진 캐시에서 전체 Release·엔진을 빌드한다. SDK는 기존 것을 읽고, 공개 NuGet 의존성은 각 checkout 전용 복사본으로 사용한다. CLI 홈·임시 파일·fixture도 실행 소유 공간에 둔다.
* 기존 실제 API/CAS, 영수증, 정상 저장·실패·응답 유실·충돌·취소·재시작/독립 창 UI 검사를 수행한다. 새 Windows 교차 패키지를 만들고 패키지 엔진·렌더러를 검사한다. 압축 후 전체 파일 집합·SHA·모드를 검증하고, 새 RAM 디렉터리에 복원한 패키지의 엔진·렌더러를 다시 실행한다.
* 명령·종료 코드·소요 시간·샘플링한 최소 디스크 여유/최대 cgroup 메모리·입력·프로필·로그·스크린샷·전체 manifest·하네스 원문을 지속 ZIP과 SHA manifest로 보존한다. fixture의 재생성 가능한 캐시/출력·프로젝트 `bin/obj`는 파일별 해시 목록을 남기고 실행 소유 임시 공간에서만 수명 관리한다. 소스와 SDK가 있어도 과거 환경을 완전히 재현한다는 보장은 하지 않는다.
* 빈 디렉터리와 모드도 새 증거 ZIP에 보존한다. 링크·특수 파일은 따라가지 않는다. 보존을 검증하지 못하면 임시물을 삭제하지 않는다.

## 프로세스와 재시작

명령은 gate를 기다리는 독립 worker로 시작한다. PID와 커널 시작 시각을 지속 기록한 뒤에만 실제 명령을 허용한다. worker는 Linux subreaper로, 별도 세션을 만든 엔진/브라우저 후손까지 종료·회수하고 완료 증명서를 남긴다. PID 핸들을 이용해 PID 재사용 시 다른 프로세스에 신호를 보내지 않는다. 제한된 FD/maps를 읽지 않는다. 명시적으로 등록한 새 Chromium 프로필의 일시적 lock/socket 링크는 대상에 접근하지 않고 링크 문자열·모드 기록으로 보존한다.

```bash
python3 tools/verification_workspace.py --recover <보관소/runs/실행ID.json>
```

재시작 복구는 기존 소유 프로세스가 종료됐고, 기록된 루트의 inode·UID·토큰·링크 경계가 같은 경우에만 처리한다. 자식 종료, 지속 증거의 파일 집합·SHA, 소유 루트를 재검증한 뒤 정확한 실행 루트만 정리한다. 중단된 지속 복사도 기록된 임시 파일 inode만 처리한다. 기존 경로를 추측하거나 glob으로 삭제하지 않는다.

통합 검사가 모두 끝난 뒤 보관 단계에서 중단됐으면 `python3 tools/verify_desktop.py --resume <실행ID.json>`으로 기존 source-bound 결과와 준비된 ZIP의 SHA를 확인하고 보관만 재개할 수 있다. 실행을 중복하지 않는다. 등록한 새 fixture 임시 디렉터리의 종료된 .NET 진단 FIFO/socket은 내용을 읽지 않고 소유·프로세스 종료를 확인해 메타데이터로 보존한다. 그 외 특수 파일은 자동 제거하지 않는다.

긴 fixture 경로에서 관측한 107바이트 .NET 소켓 이름은 같은 폴더의 완전한 진단 FIFO 이름과 유일하게 대응하고 해당 PID가 종료됐을 때만 처리한다. 전체 FIFO 이름·PID·inode·원래 소켓 경로를 남긴다. 대응이 없거나 모호하면 소켓을 보존하고 정리를 거절한다.

worker 자체가 강제로 사라져 후손 종료를 인증할 수 없으면 자동 정리를 거절한다. 가능한 부분 증거를 `partial`로 구분해 지속 보존하고 RAM 루트와 정확한 차단을 보고한다. 이는 완료 증거나 정리 허가로 사용되지 않는다. 시스템 자체가 RAM을 잃으면 미보존 실행 중 자료는 복구할 수 없다. 소스/실행 기록은 지속 저장하고, 유일한 완료 증거나 납품본은 RAM에만 두지 않는다.

## 새 패키지 보관소

기존 산출물 디렉터리를 보관소로 채택하지 않는다. 새 보관소의 신원과 등록된 archive만 관리하며 알 수 없는 파일은 보존한다. 전체 파일 SHA와 실제 복원 실행이 통과하고 증거가 지속 보존된 후보만 승격한다. 새 ZIP을 fsync·검증한 뒤 index를 원자적으로 바꾸므로 기존 최신본은 새 index가 안전해질 때까지 유지된다. index 교체 전 실패하면 기존 최신/롤백을 유지하고, 교체 후 중단되면 journal로 새 최신과 이전 최신의 롤백을 복구한다.

이 새 도구가 등록한 패키지만 최신·롤백 두 세대로 관리한다. 세 번째가 승격된 뒤 참조되지 않는 이전 관리 세대만 전체 SHA를 다시 확인하여 정리한다. 준비 후 다른 실행이 최신본을 바꿨으면 비교 검사로 거절하며 오래된 후보로 덮어쓰지 않는다. 검증된 후보의 지속 승격이 아직 필요한 RAM 루트는 정리하지 않는다. 재시작 복구는 보존된 후보와 증거를 확인하고 같은 비교 검사를 거쳐 승격을 마무리한다. 기존 과거 패키지의 보관정책은 바꾸지 않는다. 초기에는 게시본 `706ed58`을 검증·압축 보관한다. 이후 검증이 완료된 commit을 승격하고 그 직전 정상본을 롤백으로 유지한다. 각 역할의 정확한 출처 commit·전체 manifest·증거 위치는 보관소 index에서 확인한다.

## 회귀 및 한계

```bash
PYTHONDONTWRITEBYTECODE=1 python3 tests/probes/verification_workspace_test.py
```

집중 검사는 정상/실패 반복, 명령 시작 예외·타임아웃, 분리된 후손 회수, 소유 프로세스 강제 종료 후 재시작, 디스크 복사 중 강제 종료, 증거 보존 실패, 링크/루트 교체 거절, 패키지 승격 전후 실패·재시작·두 세대 복원·미등록 파일 보존을 확인한다. 실제 통합 실행의 결과/사용량은 `runs/*.json`·증거 ZIP과 실행별 콘솔 로그로 확인한다. 3–6MiB/단위는 진단 당시 가설이며 보장값이 아니다. 새 commit은 압축 패키지 보관 비용이 추가되고, 동일 commit 반복의 순증가도 실측한다.

Windows PE 교차 패키징과 Linux에서의 패키지 엔진/Chromium 실행은 실제 Windows apphost/WebView2, 모바일 기기, 전체 UI 완료, Library 전달 검증이 아니다.

* `706ed58ef27fd18739118b7c5a24f3bedda3607a`의 LF/CRLF 실제 빌드·API·기본/독립 창·새 패키지·복원 실행 34단계가 통과했다. 종료된 .NET 진단 FIFO 때문에 최초 보관이 거절됐으며, 이 항목을 읽지 않는 메타데이터 보존을 추가해 기존 결과에서 보관만 재개했다.
* 준비한 패키지 ZIP은 60,688,561바이트, 증거 ZIP은 2,334,373바이트다. 지속 보관 뒤 해당 RAM 실행 루트가 없어졌고 `/tmp` 여유는 약 9.26GB로 돌아왔다. 기존 디스크 엔진 출력·캐시를 삭제하거나 추가 생성하지 않았다.
* 지속 여유는 약 272.0MiB에서 210.6MiB가 됐다. 대부분은 의도적으로 보관한 첫 패키지의 비용이다. 실행 중 명령 단계의 최소 디스크 여유는 285,057,024바이트, 최대 cgroup 메모리는 9,093,246,976바이트였다. 이 메모리는 같은 환경의 전체 사용량이다.
* 실행 기록은 새 보관소 `runs/d9eddc9f19364cc8a4ebf698b8e281f9.json`과 그 ZIP/manifest에 있다. 최종 도구 commit의 통합 반복 결과와 최신·롤백 역할은 이후 실행 기록 및 보관소 index를 기준으로 판정한다. 이 초기 관측만으로 최종 반복 완료를 주장하지 않는다.
* 후속 `00abd44`는 실제 패키지 실패/예외 다섯 흐름을 포함한 35단계가 통과했다. 중첩 fixture의 잘린 진단 소켓도 FIFO 생산자 근거로 처리해 보관만 재개했고, 원래 34단계를 되풀이하지 않았다.
