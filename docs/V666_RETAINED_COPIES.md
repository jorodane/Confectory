`app.js::renderFeatureDefinition`/`openOwnFunctionPopover`, 기존 구현 선택과

새 복사·계약 전환 UI나 공개 override 계약 변경을 추가하지 않는다.

게시 `23df602f`에서 두 native 본문의 단일 후보와 원래 복사본 프로그램40은 유효하다.
기존 화면에서 계약을 유지한 두 본문을 편집하면 공동 후보와 UI Save만 전체 거절된다.
기존 copy receipt를 허용한 첫 제품 보완도 순수 후보 검사에서 거절됐다. 첫 함수의
명시 설명이 내부 후보에 저장된 뒤 두 번째 함수의 원래 copy context 해시와 달라지는
결합 결함이었다. 이후 첫 Review도 copy가 관측한 등록 pack header와 native unit의
읽기 범위를 결합하지 못해 거절됐다. 두 실패 입력·실행 코드·로그를 보존하고 보완했다.

직접 소유 native 그룹2–8함수와 기존 명시 target을 유지한다. 소비자는 기존 단독 배정·
single-target local copy의 정확한 출처/소유 receipt를 제출해야 한다. 원래 complete copy
proof를 먼저 검사하고, 내부에서 이미 검증·저장한 동일 계약 함수 선언의 해시만 현재
후보에 투영한다. owner·배정·graph·provenance·경로·계약과 나머지 context는 모두 같아야
한다. 이 내부 후보 연결은 실파일 변경의 새 기준이나 외부 접근 권한이 아니다.

호출만 있는 copy도 기존 version3 readGuards에 원래 source 전체를 결부한다. 기존 version3 receipt에 원래 `nativeBodyCopies` 증거도 보관해 후속 설명 Save에서
copy context를 잃지 않는다. cold에서는 이미 알려진 선언을 읽고 원래 snapshot으로
copy proof를 다시 검증한다. 실제 관측된 등록 의존성만 전체 guard의 정확한 집합에
포함하며 guard 개수 검증을 완화하지 않는다. Save 전
변경, Review 후 source/출처/배정/등록 의존성 변경, cold에서 출처가 제거된 graph, receipt 변조는
원래 snapshot/CAS로 거절한다. copy와 donor·원래 C#·핀/값/실행 연결은 읽기 의존성이며
새 쓰기 대상으로 내보내지 않는다. 원자 checkpoint·Undo/Redo·취소·실패/응답 유실·
늦은 입력·Review→Confirm 및64-member/240 read-write/2048 known unit 예산은 유지한다.

정보·참조 핀은 **정보 정의마다 별도의 C# 구조체 타입을 생성한다**는 사용자 결정을
