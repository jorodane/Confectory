# v666 500% 개인 화면 확대

기준은 [고정 수용 목록](V666_ACCEPTANCE.md)의 V1과 사용자 지정 v666 ZIP이다. 전체 v666나 기존 미완료 UI의 완료를 뜻하지 않는다.

Workspace와 native/직렬 Blueprint의 확대 범위·휠 단계·프리셋을 같은 표시 모듈에 연결했다. 원본의 400/500 프리셋, 직접 입력·범위 슬라이더·전체 보기를 직렬 Blueprint의 기존 배율 버튼에 연결한다. 100/125%만 번갈아 표시하던 동작을 원본 팝오버로 대체하며 새 메뉴나 별도 실행 기능을 만들지 않는다. 터치 확대와 저장된 화면도 같은 500% 상한을 사용한다. native 카메라의 수치 검증은 500%의 기존 허용 좌표를 복원할 수 있도록 넓히되 유한한 범위를 유지한다.

좌표·배율은 프로젝트/문서별 개인 presentation이다. 정의·본문·핀·값·소유권·기준 hash·checkpoint·CAS·Review/Confirm을 바꾸지 않는다. 원본 popup의 적용/직접 입력·Escape·바깥 클릭·초점 복귀와 창 종료/교체 callback 폐기를 유지한다. UI가 확대됐다는 이유로 source Save나 Confirm을 호출하지 않는다.

집중 검사는 실제 v666 원본 함수와 수치 범위/휠 delta mode/방향/프리셋을 대조하며, 실제 fixture 엔진/렌더러에서 Workspace·Blueprint 팝오버/입력/휠·모바일 폭의 두 접점·재시작·미저장 설명/원문 보존·창 종료를 확인한다. 기존 속성/정보 함수 카드 이미지와 늦은 입력 보존 검사를 함께 유지한다. LF/CRLF 독립 checkout과 새 Windows 교차 패키지·압축 복원본에서 실행하고 결과는 관리 실행 기록에 보존한다. 실제 Windows·모바일 기기를 실행한 것은 아니다.

실행·패키지·증거는 `tools/verify_desktop.py --suite canvas`와 기존 승인된 실행별 임시 공간/최신·롤백 보관 절차를 사용한다. 검증 완료 수와 패키지 출처는 최종 실행 기록을 기준으로 보고하며, 기존 과거 자료를 정리하지 않는다.

집중 단계에서 v666 원본 함수 대조와 76개 리소스 pin이 통과했다. native viewport 모듈의 실제 DOM에서는 500%·휠 기준점·기존 큰 카메라의 remount와 Escape를 확인했다. 이 모듈 검사는 엔진 실행으로 표시하지 않는다. 기존 직렬 renderer 회귀는 현재 저장 journal의 지속 확인/정확한 batch receipt가 빠진 테스트 provider를 먼저 발견했다. 제품의 보호를 해제하지 않고 해당 provider에 지속 snapshot·source proof·단일 삭제 검증/receipt를 구현했으며 원래 source/연결/CAS 검사는 유지했다. 수정 후 전체 renderer 회귀가 통과했다. 실패와 성공의 증거 모두 관리 실행 기록에 남긴다.

새 팝오버의 닫힌 컨트롤이 재개방한 팝오버의 배율을 변경할 수 있는 결함도 실제 DOM에서 재현했다. 현재 팝오버 인스턴스·연결·활성 창을 확인하도록 보완했으며 이전 slider/입력 callback과 abort 경계를 검사했다. 첫 독립 LF 실행은 Release/엔진/원본 대조/native 화면까지 통과했으나 새 엔진 검사에서 함수를 개념 탭으로 찾던 선택자 때문에 중단됐다. 실제 기능 탭을 선택하도록 검사 진입을 고쳤으며 이를 제품의 권한 거절이나 검사 통과로 표시하지 않는다. 제품 popup도 수정됐으므로 새 commit의 독립 빌드/패키지 검증을 다시 수행한다.

마지막 원본 대조에서는 직렬 Blueprint의 기존 Ctrl+휠 비율 곱셈/일반 휠 이동이 v666의 단계 확대와 달랐다. 일반 휠에서 500→475%가 되지 않는 것을 실제 renderer에서 재현한 뒤 Workspace/native와 같은 휠 상태기를 연결했다. 일반·Ctrl 휠 모두 포인터 기준의 원본 단계를 사용하고, 스크롤 가능한 textarea는 텍스트 스크롤을 유지한다. 직접 배율/전체 보기는 누적 휠 상태를 초기화한다. 수정 후 기존 전체 직렬 renderer 회귀가 통과했으며 실제 엔진 검사에도 500→475→500%와 plane transform 확인을 추가했다. 앞선 코드의 검사 결과는 보존하고 최종 commit을 새 독립 빌드/패키지로 다시 검증한다.

이어진 실행은 LF 전체와 CRLF의 빌드/엔진/휠 화면까지 통과했으나 모바일 폭으로 바꾼 직후 `is_visible()`로 분기한 검사가 카드 흐름 전환을 기다리지 않아 터치 시작점을 찾지 못했다. 제품 코드는 그대로 두고 실제 카드 흐름이 보일 때까지 기다린 후 기존 ‘그래프’ 버튼으로 진입하도록 검사 동기화를 수정했다. 터치는 여전히 실제 Chromium 두 접점으로 수행하고 400→500%·입력·원문 보존을 검사하며 생략하지 않는다. 실패 원인과 전환 전 DOM/화면 크기 증거를 보존한다.
