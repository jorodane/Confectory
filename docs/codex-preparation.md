# Codex preparation from Home

The current v508 Codex connection screen exposes **로그인**, with official installation/login consent only when needed, progress/cancel, failure/retry and automatic Agent registration. It does not expose runtime candidates, account folders, platform/path/model fields or advanced/manual setup. Existing settings declaration loading may still use the local authoring host. [Current validation and Windows package](validation/codex-minimal-connection-windows-package.md).

The sections below describe the retained internal installation/login safety contracts and historical validation. Their individual backend consent requirements are aggregated by the coordinator after the corresponding user-facing consent; they are not separate manual menus.

The trusted `PreparationInfo` provider selects the host's official OpenAI release asset, a pinned archive SHA-256, and storage policy. Browser inputs cannot select a download URL, digest, platform, or directory. The supported profile remains **0.159.0-alpha.3**. Existing **0.159.2** installations remain discoverable and are described as unvalidated; this change does not establish incompatibility or broaden the execution profile.

Release authority: [OpenAI's pinned release](https://github.com/openai/codex/releases/tag/rust-v0.159.0-alpha.3), whose official release asset listing supplied the six archive identities in `PreparationInfo.csbody`. Downloads allow bounded HTTPS redirects only to GitHub's release hosts. Bytes and expanded size, entries, paths and process output are bounded. ZIP and tar extraction reject traversal, absolute/drive paths, aliases, links and special entries. SHA-256 is verified before extraction or execution. A private staging directory is atomically published only after the exact version check succeeds. An operating-system file lock excludes concurrent preparation in the same managed root.

Default private storage is `%LOCALAPPDATA%/Confectory/CodexPrepared-v1` on Windows and `~/.local/share/Confectory/CodexPrepared-v1` on Linux/macOS. An unrecognized existing root is preserved; a separate bounded alternative is chosen. Every installation and login uses a fresh nonce directory. Cleanup is restricted to the current transaction's marked staging/account directory. Cancellation, form changes, close, stale consent, or settings changes cannot apply a late result to the current form. HTTP handoff, native process launch and login RPC writes check revocation under the same owner lock; cancellation that wins this lock prevents dispatch. Completed installations remain available for later discovery.

Official login consent covers the three underlying login requirements. It launches the selected CLI with a fresh owned `CODEX_HOME`, file-only CLI credential storage, a cleared environment, disabled native tools and strict configuration. The official app-server [account/login/start device-code contract](https://learn.chatgpt.com/docs/app-server) supplies the code and fixed official verification page. The engine never accepts token input, reads/copies token files, signs out, refreshes an account, or overwrites an existing account home. Cancellation clears the code, attempts `account/login/cancel`, kills only the owned process and removes only that incomplete new home. Only a matching successful completion plus `account/read` with `refreshToken:false` makes the new account directory discoverable. The executable's content fingerprint is bound to login consent, and initialization must report the validated version before login starts.

Installation and login completion continue automatically through the existing readiness/model catalogue boundaries covered by the initial connection action. Model-bound verification and every Helper request retain their independent permissions, expiry, settings/installation fingerprint, and pre-RPC dispatch fences. Preparation/login issue no thread or model turn.
