# 일반 속성 저장의 정확한 초안 검증 요청 통합

기준: `1e424a0a05ddba00bcf84e59463e78c536bef8c7`. Linux 실제 EditorHome + Chromium + .NET SDK 10.0.401. Windows 실기 미검증. 기준 tool은 HEAD 소스를 별도 디렉터리에 다시 빌드하고, 각 기준/후보 EditorHome의 실제 Build report로 실행하여 프로토콜 13/14를 혼용하지 않았다.

## 구조

- `ApplySlots`: 원래의 변경 전 단위 집합과 선언을 한 프레임으로 전달한다. 정확한 단일 루트 long/string/reference 데이터 수정에 한정한다. 기존 body/property/type 준비 검사를 순서대로 실행하고, 중간 호스트 관찰 필요 시 기존 개별 경로를 사용한다. 원본/후보의 동일성 확인, 후보 checkpoint, 기존 read guard와 최종 저장은 그대로 유지한다.
- `ValidateReviewSelection`: 같은 잠금 범위에서 property/type 검사를 한 번의 전송으로 처리한다. 별도의 관찰 검사는 기존 순서로 property observations, body headers, body graphs, body validation을 실행한다. 중간 호스트 읽기가 요구되면 일괄 결과가 완전하다고 주장하지 않고, 기존 전체 경로에서 다시 검증 및 물리 읽기를 수행한다. 원자 그룹/다른 검증은 기존 위치에 유지한다.
- `ConfirmReviewed`: 동일 workspace 잠금의 정확한 전체 단위 snapshot으로 type/property/body 검사를 순서대로 실행하고, 모든 등록 읽기 결과를 그대로 기존 최종 CAS에 전달한다. 선택 초안과 검토 기록, 최종 파일 쓰기/해시/권한/소유권 검사는 제거하지 않는다.
- Review/Confirm 불특정 경로는 확대하지 않았다. 최대 2개 선택의 단일 루트 long/string/reference object 저장 receipt만 새 경로를 사용하며 다른 선언/Worker/삭제/복구는 기존 경로다. 다른 초안의 guard 검사도 여전히 전체 입력에 대해 수행된다.
- 새로운 authoring stream protocol 14. 이전 protocol은 새로운 명령을 보내지 않고 기존 개별 요청을 사용하며, one-shot의 정확한 미지원 operation 응답도 기존 경로를 사용한다. 기존 scope, 취소, 128 frame 회수, 30초 idle 경계는 동일하다. 고정된 context menu route는 변경된 `Call.csbody`의 정확한 소스 해시를 추가하고 과거 검증된 해시를 보존했다. 첫 추가 검사에서 새 Call pin이 없어 기존 route discovery가 거절됐고, 정확한 새 pin을 추가하여 복구했다. 허용 범위/핀 검증을 완화하지 않았다.

**재사용의 범위는 정확한 동일 요청 안의 입력 데이터뿐이다.** 재사용하는 권한 결정이나 검증 결과, 외부 파일 최신성 캐시가 없다. 원본 물리 관찰, 정확한 저장/검토/최종 파일 lease는 계속 수행한다.

## 계측

실제 클릭부터 원본 파일 상태 확인(100ms polling), 저장 성공 UI, 일반 프로젝트 명령 재활성화를 나눠 기록했다. 각각 동일 창 연속 다섯 번의 중앙값이며, 처음 저장과 독립 창 저장은 별개 표본이다. CLI build 및 다른 계측과 병행하지 않는 교차를 아래 최종 표에 기록한다. 구간별 UI 스케줄링/OS 변동을 고려해 전체 latency의 범용 개선율로 해석하지 않는다.

## 보호 경로 및 프로토콜 회귀

- 실제 40/400 객체 주 창 Unicode 문자열, 독립 창 빈 문자열/정수 저장, 다른 창의 미저장 입력, 재시작 및 원본 값 확인. `strace -f`에서 두 규모 모두 일반 편집 중 compiler exec와 project DLL open 0. 읽을 수 없는 다른 소유 파일과 외부 원본 변경은 실패하고 입력/원본을 보존했다.
- 실제 400 객체 기본 창 참조 편집 및 40 객체 독립 창 참조 편집: picker와 저장 때 compiler/DLL 0/0, 명시적 Run에서 compiler 7/DLL open 84, 새 참조로 연결된 데이터 실제 실행 exit 0.
- Worker Review 취소, 동시 다른 Worker 준비, 오래된 검토 거절/입력 보존, 정확히 새 검토 후 두 번째 Worker만 채택 성공. 400 객체 역참조 보호, 삭제 취소/확정, 재시작 복구, 동일 namespace 다른 프로젝트 불변, compiler/DLL 0/0.
- 400개 8창 실제 저장 필터에서 외부 schema 갱신과 detached 미저장 입력 보존, 명시적 지도 갱신, 공개 metadata의 정확한 reference 및 틀린 token/scope 검증. `primary-external-during`, `primary-close-persist`, `stale` 통과.
- 실제 40개 동일 창 연속 저장을 protocol 13 원래 authoring tool과 새 EditorHome 조합에서도 통과하여 기존 개별 guard fallback을 확인했다. 새 요청을 legacy stream에 보내지 않는다.
- raw protocol: 기존 one-shot/stream scalar/string/reference preparation 및 guard 결과의 완전한 동등성, 실제 host source 체크 4건이 필요한 observation의 fallback, malformed receipt 에러 동등성, cross-project 종료, raw/mixed 형태 거절. read stream 전체(정확한 메뉴 pin, connection, inventory, scope, external source), 128-path optional proof 상한 보호, settings transform, 실제 257 frame 두 번 회수 및 오래된 읽기 갱신/one-shot fallback 0, 종료하지 않는 제어 worker의 강제 회수 통과.

## 남은 큰 병목

400개 `mixedOwnerCopyEdits`는 기존 동일 그래프의 full before/after `EffectiveMetadata`를 수행한다. 최종 두 readiness 교차에서 이 RPC 중앙값은 각각 127.5/154.9ms, 전체 준비 consumer 278.8/335.2ms. 현재 물리 관찰 또는 전체 소유권 검증을 생략하지 않고, 다음 구조 실험은 동일한 관찰 내에서 정확한 원본 bytes/locator의 parsing 및 읽기 모델을 공동 사용하되 각각의 검증에 독립된 draft overlay와 마지막 물리 CAS를 유지하는 방식이어야 한다. 최종 신규 성공 표시부터 실제 다음 명령 준비까지의 400개 주 창 구간은 중앙값 414.6ms였다(기준 323.3ms, 독립 창 최종 239.5ms). 관계도 자체는 이미 약 12~30ms였으므로 이 나머지 UI 전달·갱신/대기 경로를 별도로 계측해야 한다. 일반 편집 수십 ms 목표는 미완료다.

최종 추가 400개·8창 warm/cold restore 및 검색 strace의 16,225행에서 compiler exec(0), 합성 프로젝트 DLL open(0) 확인. 전체 이번 작업의 격리 브라우저 실행 52/52 통과, 매 실행 자손 잔류 0. 별도 raw read-stream 최초 실패는 위 정확한 새 pin 반영 후 통과했다. 호스트 외부 PID 1에 귀속된 Git 종료 프로세스 및 별도 SDK 빌드 서버 종료 프로세스는 강제 조작하지 않았다.
