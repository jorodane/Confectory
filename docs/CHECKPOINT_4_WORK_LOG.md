## Checkpoint 3 workflow review

Existing functional consumer actually edits App::MainBody/body:common, builds and runs the draft with changed output, then saves/closes/restores without changing final source. It confirms only the body, preserves creation drafts, confirms creation with registration, rejects invalid C#, saves again, externally changes final source and restores the saved true baseline to produce a conflict without overwriting either final or draft. Native X11 consumer exercises the same workflow with responsive peer controls and interruption. Re-run this workflow, not merely a test-count assertion.

Prerequisites identified: native attach requires an object, so engine-only/function-only projects cannot attach; editable description currently ignores all imports including project-local pins; candidate preparation points every registry path back to original source, which would validate the wrong pin if a local imported body were edited. Fix objectless attach, explicitly managed editable pin description and candidate-local relocation. External imported packs remain read-only. Core compiler self-hosting is not claimed.

## Intended PackManager increment

Confectory.PackManager::{Open,Inspect,Stage,AddHook,Apply,Dispatch,Pending,Retry,Close}. Project-local source pins under packs/<namespace>/<transaction> are explicit versions/provenance. A lock document records selected pins; no global engine update changes them. Registration/update/removal are metadata/source transactions, not runtime load/unload. Source and saves are never implicitly removed: failed/old pin directories and local saves remain available. Explicit update validates a candidate before activating; failures keep old working selection. Optional import and actual usage are reported separately.

Hooks are public function IDs with deterministic priority, ordinal ID tie order. PackManager dispatches them through the caller-selected Dispatch contract, never Core hooks. Discovery/staging/validation do not call hooks or project runtime. Completed hooks are journaled per transaction; failed hooks retry the same transaction/idempotency key. A failed hook or candidate build never activates selection. Hook external side effects are not generally rollbackable; adapters must honor idempotency keys. Unregistered routing is explicit error. Build-target packs requiring SDK bootstrap artifacts remain explicitly external/unsupported for source-only pin import until a real artifact packaging strategy exists, rather than silently copying an unusable tool.
