# V821 기본 속성 저장 후 상태 증명 재사용 (Linux Chromium)

기준: `dac0cace1ad8204c199d9cf1c6fdc23adf3c18a0`.
실측 대상: 임시 합성 40/400 객체 프로젝트, 실제 편집기 호스트와
시스템 Chromium. 모든 브라우저 실행은 `tests/run_isolated_browser_test.py`를
거쳤다. Windows 실기 검증은 하지 않았다.

## 후보 선택

처음에는 Browser 목록의 상태 그룹을 관계도 조회 응답에 포함하는
선택적 프로토콜을 구현했다. 호스트에서 동일한 초안 버전과 각 행의
리비전·해시·dirty를 확인하게 했지만, 실제 400개 저장 추적에서
`browserDrafts` 2회, `relationsMap` 1회, update 중앙값 11회가 그대로였다.
이 후보 구현을 전부 되돌렸다.

실제 요청 입력을 추적한 결과, 반복 조회는 기본 속성 편집기의
상태 읽기가 저장 전 리비전에 대기하고, 이미 저장 후 리비전의
정확한 증명을 받아도 기존 stamp를 유지하면서 발생한다. 독립 창에서
이미 사용하는 좁은 `acceptedDetachedStatusStamp` 판정을 기본 창에도
적용했다. 이 판정은 대기 중인 객체가 dirty였고, 확정 후 리비전이
정확히 1 증가했고, 동일 소스 해시·스키마 의존성 및 동일 표시 모델,
단일 소유 객체의 실제 ready/clean 행이 모두 일치할 때만 재사용한다.
호스트 읽기 자체는 여전히 수행하며, 불일치·그룹·복구·다른 소유자·
스키마 변경은 기존 재조회 경로를 유지한다.

새로운 서버 프로토콜은 없다. 물리적 Confirm 경로, 원본 소유권/권한,
작업 사본 소유자, 변경 충돌 검증, 쓰기 CAS는 수정하지 않았다.
관계도 전체 상태 응답 자체는 이번 변경에서 제거하지 않았다.

## 회귀 검증

- 40/400 문자열 및 정수 기본/독립 창, 반복 참조 값 및 실제 Run.
- 40/400 × 0/1/8 창 warm/cold 복원, 실제 일반 명령 및 검색.
- 40/400 파일 추적에서 일반 저장 compiler 0 / 프로젝트 DLL open 0,
  외부 대상 변경 및 관계없는 권한 실패 시 미저장 입력 유지.
- 40/400 관계도/작업 사본 외부 필드 갱신, 이전 프로토콜 전체 응답,
  잘못된 토큰 및 프로젝트 격리, 미저장 입력 유지.
- Worker Review 오래된 검토 채택 방지, 별도 Worker 정확한 소스 유지.
- 400개 삭제/복구/재시작/같은 ID 다른 프로젝트 보존, compiler/DLL 0.
- 기본 창 복원 중 외부 스키마, 명시적으로 닫힌 창 및 재시작,
  오래된 입장 리비전 재시도.
- `--verify-primary-status-reuse`로 기본 창 저장 뒤 중복 상태 호출 방지
  실제 40/400 브라우저 회귀 추가 및 통과.
- Node의 정확한 상태 증명 및 WebView 수명/프로젝트 격리 테스트 통과.

남은 병목은 별도 `relationsMap` 및 한 번의 실제 상태 읽기,
7~8회 상태 update, 그리고 호스트의 저장 전 준비/최종 파일 확인이다.
이 단계에서는 권위 있는 데이터 검증을 생략하지 않았다.

격리 실행 총 53회 중 51회 통과. 삭제 시험 1회는 인수 순서 오류로
실행 전 종료됐고 올바른 400개 인수로 재실행하여 통과했다. 검색
라벨 시험은 처음 한 번 창 표시 대기에서 실패했으나 기준선과 후보를
같은 순서로 다시 실행해 둘 다 통과했다. 모든 실행 결과의
`remaining` 합계는 0이고 Chromium/crashpad 잔류 프로세스는 없었다.
