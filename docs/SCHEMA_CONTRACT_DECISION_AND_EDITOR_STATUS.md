# Schema representation decision and layout-independent editor status

This audit continues `7585892`. It does not implement either schema representation, a new schema type system, semantic merge or a new UI. A small independent declared-reference inspection gap is addressed separately below. Overall editor functionality is incomplete.

## What is already decided

Readable baseline `baseline-v1.txt`, sections 2–3 and 6, establishes dedicated identity/contract/reference declarations; qualified Namespace::Element identity; single-parent inheritance with omitted items inherited, explicit values overriding and new items appended; schema item name/type, single/multiple cardinality, general/compound/function distinction, nesting/repetition, object references and function contracts/returns. Structural inheritance/containment cycles are errors; ordinary reference cycles are not universally forbidden. Schema/object/View state is separate. Section 6 expressly leaves the complete type grammar and generic/async/error/cancellation/permission/side-effect expression undefined. These established principles do not select a generic schema-item field encoding.

`docs/TECHNICAL_DESIGN.md` establishes `.celem` as one element's declaration and keeps domain-specific UI/physics/schema policies in packs. Its historical SDK8 examples are superseded by the current SDK10 migration; the declaration/ownership principles remain relevant. Current Core `Declarations.cs` accepts primitive `value` string/number/bool only; raw JSON arrays/objects and null are rejected. `Types` and `Type()` cover function-contract void/bool/int/long/float/double/string and single-dimensional arrays, with void restricted appropriately. These are function types, not a complete schema field-type contract.

`Resolution.cs::Effective` merges values by metadata key and preserves provenance, not by nested JSON member. A child `document` string replaces the whole inherited `document`. `use schema Namespace::ID` and `contain object Namespace::ID` are existing typed declaration references. A string resembling an ID inside JSON is not automatically a Core reference/dependency; an additional pack validator would have to validate it. Current source baseline/revision checks are file/unit-level in either representation; neither format supplies an automatic semantic merge.

Other decisions checked: `NEXT_EDITOR_COMPOSITION.md`, `EDITOR_SPEC_IMPLEMENTATION_MAP.md`, `EDITOR_WORKSPACE_CONTINUATION_20261008.md`, `EDITOR_SOURCE_CONFIRM.md`, `EFFECTIVE_METADATA_EXPLANATION.md`, `REQUIRED_FUNCTION_SIGNATURES.md`, `LAZY_EDIT_MATERIALIZATION.md`, SchemaEditing README and the four current pack schema declarations. No approved generic schema-item encoding was found. BaseUI BooleanSchema/ScalarSchema define bounded domain metadata (`boolean`/`int64`), not a general field grammar or a mapping to function bool/long. RigMotion and RenderAuthoring explicitly define versioned domain JSON documents stored through `value document` strings and validated by their own public pack functions. Their chosen document formats must be preserved; they do not authorize making JSON the universal schema contract.

The readable baseline has 39 parsed pages whereas the earlier requested metadata said 37; original DOCX bytes remain unverified from the earlier materialization record. This audit relies on the actual readable sections and repository contracts, not an asserted newly verified DOCX version.

## Short comparison

| Concern | JSON encoded in an existing string `value` | Formal versioned `.celem` schema-field declarations |
|---|---|---|
| Compatibility | Current parser and Save/export work unchanged. Pack must define/version/decode the document; whole-string inheritance applies. Core cannot see inner fields/references. Existing Rig/Render payloads already use this bounded pattern. | Old files must keep parsing unchanged. New syntax needs Parser/AST/protocol/cache versioning, formatter/Inspect preservation and all target/consumer tests. Existing single-parent, qualified-ID and function-type rules must remain; no implicit type widening. |
| Validation | Core validates only the outer scalar. Pack validator must enforce field identity/type/cardinality, duplicate names, references/dependencies, bounds, version and inheritance. Generic Confirm does not automatically invoke all optional domain validators. | Parser can diagnose field syntax/location and generic contract references; pack policies still validate domain constraints. It needs an explicit public validation/Confirm integration and a defined boundary, not a schema editor hardcoded into Core. |
| Difference/merge | Escaping and one-string changes obscure field deltas. Stable item IDs, canonical JSON and pack-defined diff/merge are necessary; no nested inheritance/merge is gained by using JSON. | Named AST items can support precise field deltas/provenance and clearer source diffs. Rename/delete/conflict/migration rules still need specification and tests; adding grammar does not make merge safe automatically. |
| AI editing | A tool can edit decoded JSON under a versioned pack contract, but must parse two formats, preserve escaping/unknown fields, validate qualified IDs and submit ordinary reviewed drafts. Core diagnostics stop at the outer string. | Tools can edit declared fields/contracts with source locations and existing ID/reference semantics. A public AST/edit contract and diagnostics are required; raw AI edits still need candidate validation and explicit Review/Confirm. |

Recommendation: use formal `.celem` declarations for the eventual **generic public schema-item contract**, consistent with the baseline's explicit contract/reference language; retain existing domain JSON payloads for Rig/Render. This is a recommendation, not an implementation approval or an invented grammar. If an early pack-owned JSON contract is preferred instead, document its limited inheritance/reference visibility and migration boundary before implementation. Domain-specific validation stays in packs in both choices.

Minimum decision question: **Should the first generic schema-item contract use versioned `.celem` field declarations (recommended), or a pack-owned JSON contract encoded in a string value?** Choosing `.celem` first requires a small public grammar/AST proposal for the already established name/type/cardinality/kind/reference fields and a compatibility/validation plan. Choosing JSON first requires a versioned JSON contract plus explicit whole-document inheritance/reference-validation and later migration policy. Generic/async/error/cancellation/permissions/side effects remain explicitly deferred rather than guessed.
