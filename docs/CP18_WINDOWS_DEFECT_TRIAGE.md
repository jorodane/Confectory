## Findings, not proven causes

`Window::Win32Create` creates the parent with style `0x10CF0000`, which lacks `WS_CLIPCHILDREN`. Its `WM_PAINT` copies the whole backbuffer. `NativeUI::Request` creates sibling-clipped Rich Edit children but that flag does not exclude children from **parent** drawing. Microsoft documents the separate parent clipping flag: [Window styles](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-styles). This is a concrete rendering-risk finding, not proof of the user's flicker.

`Request.windows` also sends read-only, enable, move-with-repaint and show calls on every configure, even for identical retained state. This is a second repaint/activation candidate. Measure before changing the lifecycle; do not solve flicker by replacing native text with canvas editing.

The user's subsequent clarification is that the **whole field** alternates present/absent, not ordinary caret blinking, and the second screenshot resembles the absent phase. This supports a native composition/lifecycle investigation but does not establish its root cause. Set `CONFECTORY_NATIVE_TRACE=1` before launching the Windows consumer to emit `NATIVE_UI` configure/create/frame-hide/focus/modal events and `NATIVE_WINDOW` parent-paint events. Both use Stopwatch timestamps on the same process clock. Field creation events distinguish retained controls from recreation; configure/frame-hide show requested visibility and actual parent enabled/focus state. No text value or selected filesystem path is added to this trace. Keep trace output local. Default behavior remains unchanged; tracing is deliberately opt-in because paint/configure events are frequent. Z-order and actual paint occlusion still require interactive Windows observation.

## Integration boundary before appearance work

This is a genuine child HWND, not text copied into an engine texture. Windows Rich Edit owns and paints its text/selection/caret/IME; Window owns the parent and buffered engine presentation; BaseUI owns layout, eligibility and borrowed model synchronization; NativeUI owns child identity and native lifetime. Therefore a hidden/overpainted child also loses its visible text. Matching colors cannot repair this ownership boundary, and painting a second copy of the text would introduce a second inconsistent presentation.

The supported integration must reserve/clip native child regions from parent painting, apply geometry/visibility/enabled transitions only when their retained state changes, and keep composition and focus restoration coherent with modal retirement. Visible-but-ineligible native text must remain visibly composed unless a real occlusion or screen transition requires hiding it. Treat shared-host transitions and native focus as one frame-coherent presentation decision. Validate actual select/cancel/error/repeat and direct-open paths on Windows before accepting this solution; retain OS native editing rather than canvas key handling. Styling follows this gate and cannot close it. This is a proposed solution boundary, not implemented/verified fixes in this diagnostic increment.

The native picker calls `IModalWindow::Show` on a separate STA with a borrowed parent HWND. Task completion is published inside the try/catch, before finally releases the hook/COM objects. `folder-poll` clears the dialog marker as soon as that Task completes. Audit ownership and modal teardown boundaries, including cancellation and owner close; do not unconditionally enable a parent still owned by another modal operation. [IModalWindow::Show](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-imodalwindow-show) and [EnableWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enablewindow) define the relevant OS behavior.

Home and project shell borrow the same Window through two separate native hosts. The screen transition hides the old host and switches controls/host; project chat uses a per-context retained text buffer. The ordinary event loop polls native focus **before** pumping Window messages and can subsequently route stale navigation focus. Inspect this ordering for both direct project entry and post-modal restoration; neither report implies the other.

Paired user screenshots inspected by the coordinating agent show a white/bevel lower Field before opening `Problem reports`, then a uniformly dark lower region with dimmer surrounding buttons while that top-left panel is open. The panel does not spatially overlap the Field. This is a state-dependent appearance difference, not measured flicker or proof of paint overlap. Source explains a deterministic part: `modal` is true for any shell menu; `Field(..., !modal)` sets `visible=enabled`, and NativeFrame hides absent keys. Thus the field is intentionally hidden even outside the panel's bounds, rather than merely dimmed/disabled. The retained binding is not recreated by this transition. Shared styling/occlusion must distinguish visible-but-ineligible fields from spatially covered fields; do not equate all disabled states with hidden controls. Garbled panel text is a separate source/font/localization investigation.

### Engine text disappearing with native fields

| Element | Owner / rendering | Explicit suppression |
| --- | --- | --- |
| Main Workspace label | EditorHome Label -> RenderInput DrawText -> Window Win32DrawText -> parent backbuffer | Entire label omitted when any shell menu or navigation panel makes `modal` true |
| Project description below Workspace | Same engine text path | Same `!modal` condition |

Therefore Workspace/description and the Field share an explicit screen-state hiding condition even though their paint owners differ. The top title Button does **not** share that condition. Do not assume the user's 'title' refers to description, or explain all disappearance by the Field lifecycle. If top-title output is absent while its render request remains present, investigate parent paint/invalidation/backbuffer/composition; if a role is omitted, inspect state/occlusion before the provider. Draw fills the frame then DrawText overlays text into the same backbuffer on the UI thread; both invalidate the parent. Normal message pumping happens afterward. Cross-thread modal reentrancy and paint timing still need actual Windows traces.

It adds no product title/text content. This separates missing scene output from native visibility requests and parent paint timing. Existing `HOME_UI` snapshots can corroborate state at lower cadence. New scene rebuild or common cause is not assumed.

## Coherent integration fix underway after user prioritization

User prioritizes resolving native/engine integration before backend/MEGA or further features. Navigate sometimes immediately dismisses when disappearance occurs; focus reset is the user's hypothesis. The original `navigation-dismiss` branch handles resize/focus-loss/capture-loss and outside pointer presses. `ENGINE_FLOW` now records event identity/source/type, control focus/capture/hover, navigation routing, focus requests and shell menu/navigation commands. It omits text/key payloads and records actual dismissal reasons. Windows parent activation/focus/capture/pointer messages share the same clock. Legitimate outside-click/resize/Escape must still dismiss; internal focus/paint must not.

Changes address demonstrated source-level integration faults, with Windows runtime causation still open:

* Window parent uses `WS_CLIPCHILDREN` for buffered paint; parent-to-descendant `WM_KILLFOCUS` no longer emits external View loss. Native Rich Edit likewise treats descendant moves anywhere inside its borrowed parent as internal.
* Desktop providers retain bounds/visibility/enabled/read-only state and invoke native move/show/hide/enable/editability transitions only when those states change. Frame hide skips already-hidden controls. Native text remains OS-owned; unchanged values/selection are not replaced.
* Home/Editor/game pump queued OS messages before polling model/native focus. Home/Editor request physical focus only for pointer-down or consumed navigation focus intent, rather than for every paint/focus-loss/capture event. Explicit focus requests and screen/group changes remain supported.
* Shared NativeInput Poll clears a previously native-owned model focus when the OS snapshot has no focused native control, while preserving unrelated engine button focus. Empty-background pointer presses no longer physically refocus a stale native model selection. This closes the stale model/OS focus feedback path across consumers without a screen-specific keyboard editor.
* Home no longer derives visibility directly from modal eligibility. Non-overlapping native fields remain visible but ineligible during engine modals; partial intersections clip only covered regions, rather than hiding the whole control. Engine text clips to the same spatial masks instead of globally omitting all Workspace/description text. Menu text bypasses its own underlying-content mask. Top title remains requested.
* Windows chooser has a UI-thread-owned parent disable lease. A second host cannot launch on an already-disabled parent. Poll/close wait for the dialog worker's **complete teardown**, not just early Task completion; the creating UI thread restores the parent exactly once on select/cancel/error/close, and restores saved focus only inside its own View or from no focus. Thread-start failure releases the lease. No arbitrary other disabled parent is enabled and no worker-thread SetFocus is used.

Pack intent: `Confectory.Window::Win32CreateBody`, `Confectory.NativeUI::RequestBody` desktop targets, and public-contract consumers EditorHome/MainBody, Editor/MainBody, NativeInputGame/MainBody. Existing shared signatures and Core stay unchanged. Additive `Confectory.BaseUI.NativeInput::Clip(host, fieldKey, regions)` and ClipBody request platform-neutral parent-coordinate rectangle regions (maximum 256). Existing Field had no public projection/occlusion input, so this explicit shared contract is necessary; the engine's ClipRegions output can now govern native visual **and input** regions. Windows installs an owned union HRGN through SetWindowRgn; GTK applies Cairo unions to GDK visual/input shape. The key comes from the public Field snapshot and scopes clipping to the exact retained binding; hidden project contexts with the same control ID are not altered. Providers cache bounds+region signatures and avoid reinstalling unchanged clipping. Native consumers exercise full/partial/restored clip with identity/text retained. No screen-owned interop or duplicated text painting.

Outside consumer edits are required because their event ordering and modal visibility policy were responsible for scene/focus decisions beyond provider control; native providers cannot infer application overlay state. Tests add Win32 shim parent-clip/internal-vs-external-focus assertions and actual GUI modal-visibility/retained-identity/repeated-Navigate checks. The old GUI assertion that the Workspace string must disappear from the text-request list was insufficient for spatial clipping: an emitted string can be clipped completely where its glyphs occur. The test now checks its actual clip regions exclude the menu, keeping the occlusion gate. This section describes implementation; append final verification before calling the local increment complete.

Region ownership follows [SetWindowRgn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowrgn): only successfully installed HRGNs transfer to Windows; temporary/uninstalled unions are deleted. GTK visual and input shapes follow [GDK visual shape](https://docs.gtk.org/gdk3/method.Window.shape_combine_region.html) and [GDK input shape](https://docs.gtk.org/gdk3/method.Window.input_shape_combine_region.html). GTK explicitly rejects clipping if the current display lacks visual or input Shape support; it does not silently pretend occlusion succeeded. Target capability descriptors declare implementation and required display support separately from actual runtime verification.

The actual clipping regression initially failed after the complete editing/selection sequence: requested region cache was half-width but the X server still exposed full-width. A simple initial clip-only probe succeeded, so creation-only coverage would miss it. Neither GDK-only nor GtkWidget-only shape requests closed that regression. The final Linux provider retains GTK widget shape state, drains queued toolkit work, then explicitly publishes bounding and input rectangles to the owned native XID using [X Shape extension](https://xorg.freedesktop.org/releases/X11R7.6/doc/libXext/shapelib.html). This happens on changed bounds/regions, not every frame. The actual full editing probe subsequently passed half/full server geometry, outside-region focus exclusion, visible-region focus and identity/text retention, followed by existing editing/picker/lifetime checks. Toolkit-native text ownership remains intact. No Windows conclusion is inferred from this Linux correction.

A final modal ownership audit also restricts the saved focus target itself to the picker owner's parent/descendants. GetFocus is UI-thread scoped and another View can share that thread; a stale other-View HWND must never be restored by this host. The current-focus guard alone was insufficient. This Windows-only follow-up does not change Linux behavior and requires a subsequent Windows managed build; interactive modal restoration remains unverified.
