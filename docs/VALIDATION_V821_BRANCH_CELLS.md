`0e4a03f4586805ef82c3b47a7e1fe9479529fc80`에서 기존 셀 삭제 동선을 연결했다. 편집 가능한 직접 소유 복합의 독립 명시적 case에 일반 셀이 두 개 이상 있고, 말단이 값 연결 없는 일반 `void` 셀일 때만 삭제한다. 들어오는 연결을 원래 switch 복귀점에 이어 준다. 나머지 셀, C# 파일, case 조건·라우팅·기본 경로와 값 연결을 보존한다.

기존 작업공간 형식에서 새 삭제 영수증의 내부 버전은 3이다. 정확한 자식 경로·셀 ID와 전후 그래프, 소유 선언·프로젝트·본문 원본의 해시를 유지한다. 저장·검토·확정과 복원에서 관측이 달라지면 이력을 이동하거나 원본을 덮어쓰기 전에 중단한다. 기존 단일 셀과 복합 전체를 확정해 만든 버전 1·2 영수증에 새 버전 3을 추가하고, 작업공간 재시작과 Undo/Redo 이후 기존 두 기록의 내용이 동일함을 대조했다. 직전 리더의 metadata 검증기는 실제 버전 1·2 영수증을 읽고 버전 3을 거절했다. 현재 검증기는 세 버전을 읽었다. 새 이력이 포함된 작업공간을 구버전으로 열려면 이 한계를 고려해야 한다.

격리된 LF 체크아웃에서 .NET 복원, Release, Debug MCP, Linux 편집기 빌드를 완료했다. [자식 case 삭제 UI 검사](../tests/web/v821_child_case_removal_ui.py)에서 두 재시작 경로를 검증했다. 미확정 Save 뒤 완전히 재시작해 Undo/Redo를 실행했고, Confirm 뒤 재시작한 Undo는 복원 초안만 만들었다. 그 초안을 Save하고 재시작한 뒤 별도 Review/Confirm을 거쳐 적용했다. 두 case와 기본 경로를 삭제 전·확정 후·복원 후 실행하며 선택한 말단의 출력 외에는 동작 및 반환값 합계 14가 유지됨을 확인했다.

동일한 로컬 ID를 가진 형제에서는 해당 Undo가 동작하지 않았다. 형제 원본 변경은 Save와 복원 Review 후의 Confirm을 막았고, 형제나 제거한 셀의 C#이 달라졌을 때 재시작 후 Undo는 초안과 이력을 이동하지 않았다. 공유 진입에서는 삭제가 UI에 나타나지 않았으며 마지막 셀과 다른 자식 경로는 각각 계획과 저장에서 거절됐다. 기존 루트·최상위 case·일반 자식·복합 전체 삭제/복원과 직접 소유 자식 case 재정렬도 회귀로 검사했다. 로그는 `/workspace/scratch/v821-child-case-remove-9j5m48CP`에 보존한다. 실제 Windows, 전체 UI, 목업 시각 대조는 미실행이다.

다음 구현 후보는 같은 직접 소유 case에 남은 순차 셀과 명확한 앞뒤 실행 연결이 있는 경우의 일반 중간 셀 삭제다. 최상위 case의 비말단 연결 교체와 이번 자식 case 이력 검증을 재사용할 수 있다. 마지막 셀 및 탭 자체 삭제는 빈 경로의 진입·복귀와 라우팅/복원 규칙을 먼저 정해야 한다.

## 직접 소유 복합 내부의 case 중간 셀 삭제

기존 말단 삭제와 동일한 직접 소유·단일 명시 case 연결 관측을 이용한다. case의 진입 셀은 그대로 유지하며, 앞뒤가 명확한 일반 `void` 무인수 셀은 중간에 있어도 삭제할 수 있다. 들어오는 연결을 해당 셀의 기존 다음 목적지로 이어 주고, 원래 case 반환점과 나머지 값 연결을 보존한다. 첫 셀·마지막으로 남는 셀, 값 연결이 있는 셀, 공유 진입과 별도 소유권 문맥의 제한은 유지한다.

기존 버전 3 삭제 영수증과 전체 원본 관측을 그대로 사용한다. 원본 graph와 C# 파일은 Save에서 바뀌지 않으며, Undo/Redo와 Review/Confirm은 같은 경로 및 원본 검증을 요구한다. 격리된 실제 저장 기록의 metadata 검증에서 종전 영수증 1·2·3은 이전 및 현재 도구가 모두 읽었다. 새 중간 셀 영수증 3은 현재 도구에서 통과하고 이전 도구에서는 거절되므로, 이 이력이 포함된 작업공간은 종전 리더에 대한 호환성을 주장하지 않는다.

실제 Linux Chromium [자식 case 삭제 검사](../tests/web/v821_child_case_removal_ui.py)의 `middle` 시나리오를 확장했다. 기존 도구에서는 가운데 셀이 삭제 후보가 아니었다. 현재 도구에서 삭제·Save·냉간 Undo/Redo·Review/Confirm·복원 확정 및 실행이 통과했다. 양수 경로의 `tail:7`만 삭제되고 `following:7`과 다른 분기 및 반환값 14는 그대로였다. 복원 확정 후 전체 실행 결과는 초기 결과와 일치했다. 형제 및 제거된 C# 변경과 오래된 Review는 거절되었고 원본은 보존되었다. 공유 진입 거절, 얕은 복합 전체 Undo 한 건 및 독립 저장 초안 보존, 기존 직접 속성 저장 회귀도 통과했다. `mixed` 시나리오는 병행 검사 중 첫 Save 성공 뒤 UI 대기 시간 초과가 있었으나 재실행 전체에서 이전 1·2 기록 보존 및 말단 삭제/복원과 실행이 통과했다. 같은 실제 객체 드래그를 이전/현재 도구로 교차 반복해 현재 첫 창 입력 가능 68–72.1ms, 두 번째 12.8–21.4ms를 확인했다. 병행 회귀 검사 중 측정한 값으로 엄밀한 절대 성능 비교는 아니다. 실제 Windows/WebView2는 실행하지 않았다.

## 직접 소유 복합 내부의 명시적 빈 case 삽입

기존 실행 계약에서 독립적인 case 연결이 `return:<switch-id>`를 직접 가리키는 빈 경로는 정상 실행된다. 해당 경로의 실제 분기 추가 버튼으로 일반 인수 없는 `void` 셀 하나를 넣는다. 기존 case/새 셀의 연결만 갱신하며 선택 case 외의 원래 반환점, 조건, 값 연결과 형제 소유권은 유지한다. case 연결 자체가 없거나 공유 진입인 경우는 기존과 같이 거절한다. 다른 case도 명시적으로 비어 있다는 이유만으로 별도 제한을 추가하지 않는다. 루트 복합 이동이나 기존 삭제의 허용 범위는 확대하지 않는다.

[자식 case 삽입 검사](../tests/web/v821_child_case_insert_ui.py)의 `empty`에서 Linux Chromium 실제 추가, 코드 편집, 개인 Undo/Redo, 재시작, 동일 ID의 별도 프로젝트에 대한 원래 체크포인트 거절 및 기존 입력 보존, Save/Confirm의 형제 원본 검증을 확인했다. Confirm 뒤 양수 case에 새 동작만 추가로 실행되고 음수 및 기본 경로와 반환값 합계 14는 유지됐다. 암시적 분기와 공유 진입 거절도 확인했다. 두 case가 명시적으로 빈 합성 그래프의 실행과 한 case 삽입 계획은 별도의 엔진 검사에서 통과했다. 실제 Windows/WebView2는 미실행이다.

## 남은 범위

복합/슬롯/private 내부의 구조 변경은 기존 별도 소유권·복사본·frame 관측 계약과 원자 저장 경로가 필요하다. 이번의 일반 분기 계획으로 그 권한을 넓히지 않았다. 개별 private 문맥 중 일반 메서드 자식 하나의 읽기 전용 보기는 [별도 후속 범위](VALIDATION_V821_CHILD_PREVIEW.md#직접-소유한-일반-c-메서드-자식)에 연결했다. 그 밖의 private 문맥은 별도 잔여다. 실제 Windows/WebView2·물리 기기·전체 UI·v821 원본 목업 시각 대조는 미실행이다. 이번 최종 단위는 LF 체크아웃과 Linux 앱 UI·패키지/복원을 검사하며 신규 CRLF 실행을 했다고 표현하지 않는다. 기존 v821/v666 기록은 이전 검증의 범위로 보존한다. 초기 빈 화면 원인은 미확정이다. main과 Sites는 변경 대상이 아니다.
