# Native input migration priority after the CP17 safe point

All editable text fields must use platform-native input controls. Do not add a universal hand-written shortcut/clipboard/Hangul composer to FieldInput. Preserve existing public buffer/value validation where useful; the host control owns normal editing, selection, clipboard, IME/preedit and platform conventions. BaseUI owns binding, format/validation, layout, visibility/enabled/readonly and change/submit events. Do not promise identical shortcut catalogs across platforms.

Actual current defect boundary: `BaseUI::Field/FieldInput` draw selection/caret and feed custom `TextInput`; `Window::Win32Create` handles WM_CHAR and key events for the top-level canvas only. No child EDIT/Rich Edit control exists. Pump translates/dispatched messages on its owning UI thread; it currently never bridges child native focus/value/change state. The supplied Windows IME observation reports a separate composing syllable box at the window's upper-left, detached from focused Project name/caret. This is an observer-confirmed visual symptom, not proof of duplicated characters or broken Hangul assembly. Completed Unicode injection cannot verify composition.

Windows direction: a real Unicode Rich Edit child HWND (`Msftedit.dll`, `RICHEDIT50W`) in plain-text mode supports single/multiline, OS selection/clipboard/undo/redo and IME. Microsoft documents Ctrl+A/C/X/V/Z/Y and word navigation, rather than requiring application reimplementation. The DLL and control creation must fail explicitly if unavailable. Retain one HWND per input identity, update text only for genuine external model changes so undo/selection/composition are not erased per render. Own handles/callback roots on creating UI thread; child controls close before parent/native session. Keep WM_COMMAND/change, native focus and the common model coherent, suppress canvas text input when a native field owns it. Application Tab/submit/Escape routes must not steal IME composition keys. Avoid exporting control clipboard contents; tests seed synthetic data only.

Linux direction: installed GTK3/GDK and GtkSourceView4 are available. Linux has no single Win32-equivalent built-in text-control API; a GTK native widget provider needs a correct toolkit host/event-loop/focus relationship to existing X11 surfaces. Gtk.Entry is single-line, Gtk.TextView is multiline; their native IM context/clipboard facilities are documented. GtkSourceView can serve source-editing requirements if its existing dependency is explicitly selected and verified. Do not reparent foreign toolkit widgets into the canvas and claim reliable input without testing XEmbed/focus/resize/clip/close. This adapter is not implemented yet. Keep unsupported capability visible rather than silently falling back to custom editing.

Android direction: app-owned EditText on UI thread, Activity/Surface lifecycle and InputMethodManager. Current desktop consumer explicitly rejects Android runtime. Java21 runtime is present; `javac`, `adb` and `sdkmanager` are absent here. Managed target compile is not an Android app/native-control build. No tool installation or license acceptance is performed.

Hosting contract requirements before implementation: explicit parent surface/View identity and native capability; create/update/focus/snapshot/close; monotonic change identity/value vs external write; readonly vs disabled; clipped visible client rectangle and scroll; opaque overlay/modal occlusion; retained input lifetime across screen changes/context changes; focus leave/cancel/composition policy; owner cleanup and threading. Game/editor consumers use the same BaseUI API. Native child UI may overlap hardware/canvas rendering; any windowless Rich Edit or render-texture path is separate advanced scope, not a shortcut to user-approved actual native controls.

Acceptance: editor and editor-free consumer, real single/multiline native controls, synthetic select/copy/cut/paste/undo/redo and conventional navigation samples, focused View isolation/readonly/disabled, resize/scroll/popup overlap, external value update, repeated hide/show/close/reopen and UI-thread cleanup. Windows Korean IME requires actual enabled Korean IME: preedit/commit/cancel, focus changes and candidate/composition placement relative to caret. This environment has no Windows runtime/Wine/cmd/PowerShell, so managed compilation cannot close that gate. Do not claim IME acceptance from font rendering or completed-string injection.

Primary references consulted:
- [Microsoft Rich Edit controls, versions, IME and shortcut keys](https://learn.microsoft.com/en-us/windows/win32/controls/about-rich-edit-controls)
- [GTK3 Entry](https://docs.gtk.org/gtk3/class.Entry.html)
- [GTK3 TextView](https://docs.gtk.org/gtk3/class.TextView.html)
- [Android EditText](https://developer.android.com/reference/android/widget/EditText)

This document records the required migration and inspected provider gap, not a delivered native-input implementation. CP17 preserves existing Field behavior solely while finishing its unrelated bounded navigation slice; the production native migration remains the immediate next task.

## Native filesystem dialog boundary

User also requires actual filesystem folder selection to use the platform-native picker. Current `EditorHome::Browse` switches to a custom browse screen and `FileStream::BrowseDirectory` enumerates directory rows; that is a backend enumeration service, not a native picker. Keep enumeration for non-UI consumers as needed, but stop using its rows as the production filesystem-picker UI. Concept/Pack/semantic navigation remains Confectory UI and is distinct.

Next shared native dialog contract must specify explicit owned parent surface/View, initial directory, completion/cancel, owner cancellation and validated selected path, without broader filesystem grant. Windows priority is an OS folder dialog (`IFileOpenDialog` folder mode) with correct COM apartment/UI thread/modal owner and balanced COM lifetime. The existing Task.Run command worker cannot blindly invoke an STA-bound dialog. Linux native chooser needs GTK/portal capability and correct existing X11 parent/focus/modal lifecycle. Android needs the app-owned system document-tree picker and persisted granted URI semantics; it cannot return a guessed desktop path. Report missing provider/platform permission rather than silently show the custom browser.

Audit file-open/save dialog callers separately from backend reads/atomic save. Current production UI exposes folder-project opening and parent-folder selection; there is no inspected production generic file-open/save dialog to claim migrated. FileStream persistence/validation remain legitimate services. Folder opening already uses explorer.exe/xdg-open; this is OS behavior, though consumer-direct launching should later sit behind a shared service contract. Native titlebar/window move/minimize/maximize/close already delegates to OS; no reason to rebuild it. Fonts/metrics use native APIs, but native text editing/IME and filesystem chooser remain actual gaps. Buttons, rounded menus, semantic discovery and game overlays are custom product rendering and are not automatically required to be native widgets by these corrections.

Concise replacement inventory: (1) custom text selection/caret/edit/clipboard/IME → actual native text controls; (2) custom filesystem chooser rows → OS folder picker; (3) future user-facing file-open/save dialogs → OS dialogs, separately from backend atomic write; (4) consumer-direct folder launch → shared native service. This is an inspected boundary inventory, not a delivered dialog/control migration. Supplied folder screenshot identity is recorded in the parent task; pixels were not inspected in this slice, and no visual diagnosis is claimed from its filename.

## Actual build-target/provider separation

A build-target pack already exists: `Confectory.Build.DotNet` registers `Portable` and `Linux` buildtarget elements in `targets/dotnet/pack.cpack`. EditorHome maps target `linux` to Linux, and `windows`/`android` to Portable. There are no separate windows.celem/android.celem backend files in that pack. These elements compile/package managed code; they do not supply a native text control or filesystem dialog merely because a target profile compiled.

Runtime feature contracts are separate packs: Window owns surface/capabilities/native providers; RenderInput owns pump/draw/text measurement contracts; BaseUI owns common widgets/model binding. Target-specific implementation bodies already exist (`Window::CapabilitiesBody` has android/common bodies), while desktop common bodies currently dispatch to Win32/X11 implementations using runtime OS detection. Existing minimal core selects public namespace+elementID contracts and target bodies; no engine-specific host redesign is needed.

Native migration should add public platform-neutral text-control/dialog/capability requests and target-specific providers via the existing target selection mechanism. Consumers request those functions; they must not multiply OperatingSystem checks or implement editing/chooser semantics in each screen. The compiler backend remains compilation/toolchain ownership. A target may declare/build-link native runtime providers, but missing native service capability must fail explicitly rather than masquerade as successful managed compilation. No such new runtime provider has been implemented or published by this assessment.
